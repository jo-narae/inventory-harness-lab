# 00. SSOT

> 이 문서는 저장소에서 어떤 질문을 어디에서 판단할지만 정한다.
>
> 실제 내용은 각 원본에 두며, 여기에는 복사하지 않는다.

## 0. 원칙

1. 책임 영역마다 원본은 하나만 둔다.
2. 참고 문서와 원본이 다르면 원본을 따른다.
3. 도메인·아키텍처·운영 기준이 바뀌면 원본을 먼저 수정한다.
4. 원본에 없는 도메인·아키텍처·운영 결정은 임의로 정하지 않는다.
5. 원본을 새로 만들거나 옮기면 이 표도 함께 갱신한다.

## 2. 책임 경계

### 재고 도메인

`docs/01-requirements.md`는 재고의 개념, 기능, 업무 규칙과 제품 완료 기준을 정한다.

기술 구조와 구현 방법은 다루지 않는다.

### 아키텍처

`docs/06-architecture.md`는 기술 스택, 파일 구조, 데이터 모델과 재고 처리 구조를 정한다.

검증을 언제 어떻게 실행할지는 다루지 않는다.

### 검증 규칙

`docs/harness/02-verification.md`는 무엇을 통과해야 변경이 끝난 것인지 정한다.

기계 검증의 단계 구성과 순서, 게이트와 경고의 구분, Issue 단위 검증의 형식,
한 번의 실행 안에서 어느 단계가 멈추면 뒤 단계를 건너뛰는지를 정한다. CI가 PASS한 뒤 도는
LLM 검토를 어느 자리에 두고 그 결과에 어떤 구속력을 주는지, 사람 검증을 언제 누가 무엇을
대상으로 하는지도 정한다.

검증 항목의 내용 자체는 정하지 않는다. 도메인 수용 기준은 `01`, 불변식은 `06`, 이번 작업의 종료 조건은 Issue가 정한다.

검증을 어떤 순서로 몇 번 반복할지도 다루지 않는다.

### 구현·검증 루프

`docs/harness/03-loop.md`는 검증 판정 이후 무엇을 하는지를 정한다.

반복(시도)의 단위, 최대 반복 횟수, 반복 중 `NEEDS_HUMAN`을 선언하는 시점과 사유별 보고
내용을 정한다. 로컬 판정이 끝난 변경이 언제 PR로 넘어가고, CI·LLM 검토·사람 검증의 결과를
받아 루프의 어디로 돌아오는지도 정한다. Issue와 PR에 남기는 코멘트의 양식도 여기서 정한다.

검증 항목의 내용이나 게이트·경고의 구분은 다루지 않는다. 그것은 `02`의 몫이다.

### 개별 작업

GitHub Issue는 이번에 무엇을 변경하고, 무엇을 만족하면 끝나는지를 정한다.

작업 중 도메인이나 아키텍처 결정이 바뀌면 Issue만 수정하지 않고 해당 원본을 먼저 갱신한다.

## 4. 충돌 정책

| 충돌 | 처리 |
|---|---|
| 참고 문서 ↔ SSOT | SSOT를 따르고 불일치를 보고한다 |
| Issue ↔ SSOT | `NEEDS_HUMAN`을 선언하고 사람의 판단을 기다린다 |
| SSOT ↔ SSOT | `NEEDS_HUMAN`을 선언하고 사람의 판단을 기다린다 |

AI는 충돌이 확인되면 위 표가 정한 처리 외에 자신의 판단으로 어느 한쪽을 선택하지 않는다.

어느 쪽이 옳아 보이더라도 그 판단으로 작업을 진행하지 않는다.

### `NEEDS_HUMAN` 선언

`NEEDS_HUMAN`은 자동화된 판단이나 반복을 멈추고 사람에게 넘길 때 선언하는 공통 신호다.
무엇이 이 신호를 트리거하는지, 어떤 형식으로 보고하는지는 상황마다 다른 원본이 정한다.

| 트리거 | 정의 위치 |
|---|---|
| 원본 간 충돌 (Issue ↔ SSOT · SSOT ↔ SSOT) | 본 절 (§4) — 아래 4항목 형식 |
| 반복 구현 중 정지 사유 | `docs/harness/03-loop.md` |

공통 규칙: 판단을 받기 전까지 그 사유에 의존하는 변경은 하지 않는다. 무관한 작업은 계속한다.
판단이 나오면 사람의 결정에 따라 해당 원본·Issue·작업 상태를 갱신하고 재개한다.

충돌의 경우 다음 네 가지를 적어 보고한다.

1. 충돌한 두 지점 — 파일과 절 번호, Issue 번호
2. 각각이 말하는 내용
3. 어느 쪽을 선택하느냐에 따라 달라지는 결과
4. 사람이 답해야 할 질문 한 줄

## 5. 보호 영역과 소유권

영역마다 AI가 할 수 있는 일과 사람의 권한을 나눈다.

| 영역 | AI | 사람 |
|---|---|---|
| 애플리케이션 코드 | Issue 범위 안에서 수정 | 최종 승인 |
| Issue별 테스트 | 작성·수정 | 전제 검토 |
| 요구사항·아키텍처 | 읽기 | 변경·승인 |
| 하네스 핵심 규칙 | 읽기 | 변경·승인 |
| 검증 스크립트 | 실행 | 정책 변경 승인 |

이 저장소에서 각 영역이 가리키는 것은 다음과 같다.

| 영역 | 대상 |
|---|---|
| 애플리케이션 코드 | `src/`, `prisma/` |
| Issue별 테스트 | `tests/issues/` |
| 요구사항·아키텍처 | `docs/01-requirements.md`, `docs/06-architecture.md` |
| 하네스 핵심 규칙 | `docs/harness/`, `AGENTS.md`, `CLAUDE.md` |
| 검증 스크립트 | `scripts/verify/` |

AI는 사람의 변경 권한에 속한 영역을 직접 확정하지 않는다.

변경이 필요하면 변경안과 이유를 제시하고 사람의 승인을 기다린다. 사람의 명시적인 수정 요청은 해당 변경에 대한 승인으로 본다.

0절 3번의 “원본을 먼저 수정한다”는 원본 변경 권한까지 AI에게 준다는 뜻이 아니다. AI는 변경안을 제시하고, 사람의 승인 후 원본을 먼저 갱신한다.

Issue 범위를 벗어나는 변경이 필요하면 작업을 진행하지 않고 사람에게 Issue 범위 변경을 요청한다.

### 승인 기록

보호 영역의 변경 승인은 검사가 확인할 수 있는 기록으로 남긴다.

| 방법 | 적는 곳 | 유효 범위 |
|---|---|---|
| 커밋 트레일러 | `Approved-Protected: <경로>` | 로컬·CI |
| 환경변수 | `ALLOW_PROTECTED="<경로>"` | 해당 로컬 실행 |

예:

    Approved-Protected: docs/harness/00-ssot.md scripts/verify/

CI에서 통과시켜야 하는 승인은 커밋 트레일러로 남긴다. 환경변수는 로컬 실행에서만 사용한다.
