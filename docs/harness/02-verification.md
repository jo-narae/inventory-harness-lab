# 02. 검증 규칙

> 이 문서는 **무엇을 통과해야 변경이 끝난 것인지**만 정한다.
>
> 재고 규칙과 아키텍처 규칙 자체는 여기서 정하지 않는다. 그것은 `docs/01-requirements.md`와
> `docs/06-architecture.md`의 몫이고, 이 문서는 그 규칙들을 **언제 어떻게 판정하는지**를 정한다.

## 0. 범위

| 정한다 | 정하지 않는다 |
|---|---|
| 검증의 층(기계·LLM·사람)과 각 층의 판정 방법 | 재고 개념·기능·업무 규칙 (`01`) |
| 공통 기계 검증의 단계 구성과 순서 | 데이터 모델·재고 처리 구조 (`06`) |
| 단계별로 무엇을 잡고 무엇을 안 잡는가 | 이번 작업의 범위와 종료 조건 (GitHub Issue) |
| 게이트와 경고의 구분, 검사 불능의 처리 | 최대 반복 횟수와 그 출처 (`03-loop.md`) |
| LLM 검토를 어느 자리에 두고 그 결과에 어떤 구속력을 주는가 | 검토 결과와 판정 결과를 남기는 코멘트의 양식 (`03 §5`) |
| Issue 단위 검증의 형식과 대응 규칙 | 반복을 멈추고 사람에게 넘기는 시점과 형식 (`03-loop.md`) |
| 한 번의 실행 안에서 어느 단계가 멈추면 뒤 단계를 건너뛰는가 | 재시도 자체를 멈추는 기준 (`03-loop.md`) |

검증 항목의 **내용**은 원본에서 온다. 이 문서에 도메인 수치나 불변식 목록을 옮겨 적지 않는다.

두 벌이 되는 순간 어느 쪽이 맞는지 알 수 없어진다.

| 검증 항목의 출처 | 원본 |
|---|---|
| 제품 수용 기준 | `01 §7` 완료 기준 |
| 자동 테스트로 지킬 불변식 | `06 §9` |
| 재고 변경 경로 규칙 | `06 §2` · `§4.1` · `§7.5` |
| 보호 경로와 승인 형식 | `00-ssot.md §5` |
| 이번 작업의 종료 조건 | 해당 Issue의 종료 조건 |

## 1. 검증의 세 층

| 층 | 판정자 | 구속력 | 대상 | 현재 상태 |
|---|---|---|---|---|
| **기계 검증** | `npm run verify` | 게이트 | 코드·데이터 불변식, 경로 규칙, 타입·린트·빌드 | 확정 (§2) |
| **LLM 검토** | AI | 경고 | 규칙으로 적히지 않은 어긋남 — 의도와의 차이, 판정이 비는 자리, 구조 | 확정 (§5) |
| **사람 검증** | 사람 | 게이트 | 시나리오 재현·반응형·엣지 케이스 (`07 §2 B~D`) | 확정 (§6) |

세 층은 이 순서로 지나간다. 기계 검증이 로컬과 CI에서 판정하고, CI가 PASS한 뒤 LLM 검토가
돌며, 그 결과를 입력으로 사람이 마지막에 판정한다 (`03 §6.2`).

**기계 검증을 통과하지 못한 변경은 완료가 아니다.** 사람 검증은 기계 검증을 대신하지 못하고,
기계 검증도 사람 검증을 대신하지 못한다. LLM 검토는 그 둘 중 어느 쪽도 대신하지 못한다 —
지적이 없다는 결과가 기계 검증이나 사람 검증을 면제하지 않는다.

층마다 구속력이 다른 이유는 §3이 정한다.

## 2. 공통 기계 검증 — `npm run verify`

한 명령이 전부다. 단계를 낱개로 돌리는 것은 개발 중 확인일 뿐, 판정이 아니다.

```
Protect → Prepare → Types → Lint → Arch → Test → Domain → Build
```

| 단계 | 잡는 것 | 잡지 않는 것 |
|---|---|---|
| Protect | 사람 소유 영역이 승인 없이 바뀌었는가 (`00-ssot.md §5`) | 그 변경이 옳은가 |
| Prepare | — 판정이 아니라 준비다. 검증용 DB를 매 실행 같은 상태로 되돌린다 | — |
| Types | 타입 오류 | 실행했을 때의 동작 |
| Lint | 정적 규칙 위반 | 동작의 옳고 그름 |
| Arch | 재고 변경이 정해진 경로와 트랜잭션 규칙을 지키는가 (`06 §2` · `§4.1`) — 정적으로 | 실행 결과가 맞는가 |
| Test | `tests/`의 공통 불변식과 `tests/issues/`의 Issue 전용 테스트 | 테스트가 없는 규칙 |
| Domain | 시드가 만든 실제 데이터가 도메인 수용 기준과 맞는가 | 코드 품질 |
| Build | 빌드가 통과하는가 | 화면이 실제로 맞게 보이는가 (사람 검증의 몫) |

각 단계가 무엇을 검사하는지의 내용은 원본에 있다. 이 표는 어느 단계가 무엇을 맡는지만 가른다.

### 단계 중단과 건너뛰기

`npm run verify`는 한 줄로 이어진 명령이라 먼저 실패한 단계에서 멈춘다. 뒤 단계는 실행되지
않는다.

그래서 한 번의 실행이 보고하는 실패는 언제나 하나다. 뒤 단계가 통과할지는 그 실행으로 알 수
없다. 앞 단계를 고친 뒤 다시 돌려야 알 수 있고, 그 다시 돌리는 것은 `03`이 세는 다음 시도다.

## 3. 게이트와 경고

게이트는 통과하지 못하면 그 변경이 완료가 아닌 판정이다. 경고는 완료를 막지 않는 판정이다.

| 구분 | 여기에 속하는 것 |
|---|---|
| 게이트 | `npm run verify`의 모든 단계 (Prepare 제외, §2) · 사람 검증 (§6) |
| 경고 | LLM 검토 (§5) |

Prepare는 판정이 아니라 준비다. 그 외에 `npm run verify`에 포함된 단계는 전부 게이트이고,
하나라도 통과하지 못하면 그 변경은 완료가 아니다.

어떤 단계를 경고로 낮추려면 이 문서를 먼저 고친다. 스크립트에서 조용히 빼거나 실패를 무시하는
것으로 대신하지 않는다.

### 경고가 완료를 막지 않는다는 것의 뜻

경고의 지적을 받아들일지는 사람이 정한다. 그러나 그것은 **돌리지 않아도 된다**는 뜻이 아니다.
경고 층도 정해진 자리에서 반드시 실행하고, 결과를 반드시 남긴다 (§5).

실행하지 않은 것을 지적이 없는 것으로 보고하지 않는다.

### 검사 불능

게이트 단계가 판정을 내리지 못한 채 끝나면 — 환경이 갖춰지지 않았거나, 도구가 오류로 죽었거나,
시간이 넘었거나 — 실패로 본다.

판정하지 못한 것은 통과한 것이 아니다.

## 4. Issue 단위 검증

공통 기계 검증은 저장소 전체의 규칙을 본다. 이번 Issue의 종료 조건은 그 Issue의 전용 테스트가
판정한다.

| 항목 | 규칙 |
|---|---|
| 어디에 두나 | `tests/issues/issue-<번호>-<기능명>.test.ts` |
| 무엇을 적나 | Issue 폼 4번 칸에 종료 조건과 그것을 판정하는 테스트를 적는다 |
| 언제 도나 | 공통 기계 검증의 Test 단계에서 함께 돈다. 따로 돌리는 것은 판정이 아니다 |
| 종료 조건에 대응 테스트가 없으면 | 무엇으로 판정할지 Issue에 먼저 적고 돌린다 (`AGENTS.md §3`) |
| 다른 Issue의 테스트 | 고치지 않는다. 고쳐야 하면 Issue 범위를 벗어난 것이다 (`03 §4`) |

## 5. LLM 검토

기계 검증은 규칙으로 적을 수 있는 것만 판정한다. 규칙으로 적히지 않은 어긋남 — 구현이 종료
조건의 글자는 맞췄지만 의도와 다른 방향인 경우, 새로 생긴 규칙을 판정하는 것이 아무것도 없는
경우 — 은 통과한 채로 지나간다. 그 자리를 사람에게 넘기기 전에 한 번 훑는 층이다.

| 항목 | 규칙 |
|---|---|
| 시점 | CI가 PASS한 뒤, 사람 검증을 요청하기 전 (`03 §6.2`) |
| 실행자 | AI. 로컬에서 검토하고 결과를 그 PR에 코멘트로 남긴다 |
| 대상 | 이 PR의 diff와, 그 diff가 닿은 원본 — 해당 Issue의 종료 조건 · `01` · `06` |
| 보는 것 | 구현이 종료 조건·원본의 의도와 어긋나는가 · 판정하는 것이 없는 자리가 생겼는가 · 놓친 엣지 케이스 · 뒤에 유지보수를 어렵게 할 구조 |
| 보지 않는 것 | 기계 검증이 이미 판정한 것 — 타입·린트·경로 규칙·불변식. 통과한 것을 다시 훑어 중복으로 적지 않는다 |
| 구속력 | 경고다 (§3). 지적이 남아 있어도 사람 검증으로 넘어간다 |
| 시도 횟수 | 세지 않는다. 구현과 `npm run verify`의 묶음이 아니다 (`03 §1`) |
| 결과 기록 | 지적이 없어도 PR에 코멘트로 남긴다. 양식은 `03 §5` |
| 지적의 처리 | 사람이 정한다. 고치기로 하면 사람 검증 반려와 같은 경로로 돌아간다 (`03 §6.3`) |

경고로 두는 이유는 이 판정이 재현되지 않기 때문이다. 같은 diff에 같은 지적이 다시 나온다는
보장이 없고, 지적의 근거가 원본에 없을 수도 있다. 재현되지 않는 판정을 완료를 막는 자리에
두면 무엇이 통과 기준인지 알 수 없어진다. 그래서 판정이 아니라 사람이 읽을 재료로만 쓴다.

지적이 없다는 결과는 "찾지 못했다"는 뜻이지 "문제가 없다"는 뜻이 아니다. 자기 변경을 자기가
훑은 것이므로 통과 판정으로 읽지 않는다.

검토를 돌리지 못했으면 돌리지 못했다는 사실을 코멘트에 적는다 (§3).

검토 중에 원본끼리 또는 Issue와 원본이 어긋나 있는 것을 발견하면 그것은 검토 지적이 아니라
충돌이다. `00-ssot.md §4`가 정한 대로 `NEEDS_HUMAN`을 선언하고 멈춘다 (`03 §4`).

## 6. 사람 검증

기계 검증이 통과하고 LLM 검토가 끝난 뒤에도 남는 것을 사람이 본다. 화면이 실제로 맞게 보이는지,
흐름이 실제로 이어지는지는 `npm run verify`가 판정하지 못한다.

| 항목 | 규칙 |
|---|---|
| 시점 | CI가 PASS하고 §5의 검토 코멘트가 남은 뒤, 머지 전 |
| 판정자 | 사람. AI는 검증을 요청하고 기다린다 |
| 대상 | `07 §2` 체크리스트 B~D 중 이번 Issue가 건드린 화면·흐름에 해당하는 항목 |
| 입력 | §5의 LLM 검토 코멘트. 받아들일지는 사람이 정한다 |
| 통과하면 | 사람이 머지한다 |
| 반려하면 | `03 §6.3`이 정한 자리로 돌아간다. 시도 횟수는 0으로 초기화된다 |
| 결과 기록 | 통과·반려 모두 PR에 코멘트로 남긴다 (`03 §5`) |

전체 체크리스트를 매 Issue마다 다시 돌리지 않는다. 이번 변경이 닿지 않은 항목은 앞선 검증에서
이미 판정된 것으로 본다.

`07`은 참고 문서다. 항목의 내용이 바뀌면 그쪽을 고친다. 이 문서는 무엇을 언제 누가 보는지만
정한다.

LLM 검토의 지적은 이 층의 입력일 뿐이다. 사람이 그것을 받아들여 반려해도, 무시하고 통과시켜도
그 판단이 최종이다. 지적이 남아 있다는 사실 자체는 통과를 막지 않는다 (§3).

사람 검증은 기계 검증을 대신하지 못한다 (§1). 기계 검증을 건너뛰고 사람 검증만으로 완료를
선언하지 않는다.
