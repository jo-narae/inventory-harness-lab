# 03. 구현·검증 루프

> 이 문서는 **02가 내린 판정 이후에 무엇을 하는지**만 정한다.
>
> 무엇을 통과해야 끝인지, 게이트와 경고를 어떻게 나누는지는 `docs/harness/02-verification.md`의
> 몫이다. 이 문서는 그 판정을 입력으로 받아 언제 다시 시도하고, 몇 번까지 반복하며,
> 언제 반복을 멈추고 사람에게 넘기는지를 정한다.

## 0. 범위

| 정한다 | 정하지 않는다 |
|---|---|
| 반복(시도)의 단위 | 무엇이 게이트이고 무엇이 경고인가 (`02`) |
| 반복을 다시 시작하는 조건과 멈추는 조건 | 검사 불능의 처리 (`02`가 이미 실패로 정함) |
| 최대 반복 횟수의 출처와 세는 방법 | 이번 작업의 종료 조건 (Issue) |
| 반복 중 `NEEDS_HUMAN`을 선언하는 시점과 사유별 보고 내용 | `NEEDS_HUMAN` 선언의 정의 자체 (`00-ssot.md §4`) |
| PR로 넘어가는 조건과 CI·사람 검증 결과를 받아 돌아오는 지점 | CI 워크플로의 구성과 검사 내용 (`.github/workflows/verify.yml` · `02`) |
| CI·사람 검증을 시도 횟수에 어떻게 반영하는가 | 사람 검증의 시점·판정자·대상 (`02 §5`) |

이 문서는 `npm run verify`가 무엇을 검사하는지 다시 적지 않는다. 검사 내용이 바뀌어도 이
문서는 그대로 유효해야 한다.

## 1. 반복의 단위

1회 시도(iteration)는 다음 둘을 묶은 것이다.

1. Issue 범위 안에서의 구현 변경
2. 그 변경에 대한 `npm run verify` 1회 실행

`npm run verify`를 몇 번 돌렸는지가 아니라 이 묶음이 몇 번 반복됐는지를 센다. 구현을 여러 번
고쳐도 검증을 한 번만 돌렸다면 아직 1회 시도가 끝나지 않은 것이다.

정상적인 시도는 구현과 그에 대한 `npm run verify` 1회로 끝나고, 시도 횟수는 그 시점에
오른다. PASS든 FAIL이든 결과와 무관하다 — 검증이 끝났다는 사실 자체가 1회 시도를 완료시킨다.

여기서 세는 `npm run verify`는 로컬 실행이다. PR에서 도는 CI 실행은 이 묶음이 아니므로 시도로
세지 않는다 (§6.2).

다만 구현 도중 §4의 즉시 사유로 `NEEDS_HUMAN`이 선언되면, 검증까지 가지 않았더라도 그
시도는 1회를 소진한 것으로 센다.

## 2. 반복 흐름

```
Issue 확인 → 구현
                │
        구현 중 §4 즉시 사유 발생?
            │              │
           예              아니오
            │              │
      시도 횟수 +1     npm run verify → 시도 횟수 +1
      NEEDS_HUMAN              │
                    ┌──────────┴──────────┐
                   PASS                  FAIL
                    │                      │
            종료 조건 전부 대조      §4의 즉시 사유에 해당?
                    │                  │        │
              완료 보고 (§5)          예        아니오
                                       │        │
                                 NEEDS_HUMAN   최대 횟수(§3) 도달?
                                                   │        │
                                                  예        아니오
                                                   │        │
                                             NEEDS_HUMAN   원인 분석 → 재구현 → 다시 npm run verify
```

구현 중 발견되든(위 왼쪽 갈래) `npm run verify` 결과로 확인되든(오른쪽 갈래), §4 즉시 사유는
어느 시점에 걸려도 그 시도를 1회 소진한 것으로 세고 곧바로 `NEEDS_HUMAN`으로 간다.

같은 단계가 같은 원인으로 다시 실패해도, 최대 횟수 안이라면 반복을 계속한다. 원인이 같다는
사실 자체는 반복을 멈추는 근거가 아니다.

완료 보고까지 끝난 변경이 어디로 가는지는 §6이 정한다. PR과 CI는 이 그림 밖에 있고, CI 결과로
돌아올 때 위 그림의 FAIL 갈래에 다시 붙는다 (§6.2).

## 3. 반복 구조 — 최대 횟수

- 이슈마다 정한다. 출처는 `.github/ISSUE_TEMPLATE/maintenance.yml` 6번 칸(1·2·3·5회, 기본 3회)이다.
- 세는 대상은 §1의 "1회 시도"뿐이다.
- 폼을 거치지 않은 Issue는 최대 횟수가 적혀 있지 않다 (§7 미정 1번).
- 카운터는 Issue마다 하나다. 사람 검증 반려로 0이 되고, 그때부터 다시 센다 (§6.3).

기본값 3회를 예로 들면 구조는 다음과 같다.

```
1차 시도  구현 → npm run verify → FAIL → 원인 분석
2차 시도  재구현 → npm run verify → FAIL → 원인 분석
3차 시도  재구현 → npm run verify → FAIL → 최대 횟수 소진 → NEEDS_HUMAN
```

어느 시도에서든 PASS + 종료 조건 전부 참이면 그 시점에 바로 완료로 끝내고, 남은 횟수는
채우지 않는다.

## 4. `NEEDS_HUMAN`을 선언하는 시점

`NEEDS_HUMAN` 선언 자체의 정의와 공통 규칙은 `00-ssot.md §4`가 정한다. 이 절은 반복 구현 중
그 신호를 언제 쓰는지와, 사유별로 무엇을 보고하는지만 정한다.

| 시점 | 횟수와의 관계 | 보고 내용 |
|---|---|---|
| Protect 단계 실패 (보호 경로 변경 필요) | 무관 · 즉시 | 바꿔야 할 경로와 이유 |
| Issue ↔ 원본, 원본 ↔ 원본 충돌 발견 | 무관 · 즉시 | `00-ssot.md §4`의 4항목 형식 |
| 구현 중 Issue 범위를 벗어나는 변경이 필요해짐 | 무관 · 즉시 | 넘어서게 된 지점과 필요한 범위 변경 |
| CI 실패가 로컬 `npm run verify`에서 재현되지 않음 | 무관 · 즉시 | 실패한 단계, CI 실행 위치, 로컬에서 재현을 시도한 결과 |
| 최대 시도 횟수 소진 (마지막 시도까지도 FAIL) | 횟수 소진 후 | 시도별 변경 요약, 마지막 실패 원인, 판단 요청 질문 1줄 |

마지막 줄을 뺀 넷은 남은 횟수와 무관하게 즉시 적용된다. 최대 시도 횟수 소진만 횟수를 다 쓴 뒤에
적용된다.

앞의 셋은 구현 도중에 걸릴 수도, `npm run verify`의 FAIL로 확인될 수도 있다. 어느 경우든
그 시도는 1회를 소진한 것으로 센다 (§1).

CI 재현 불가는 PR을 연 뒤에만 확인된다 (§6.2). 그 시도는 앞서 로컬 검증으로 이미 1회 세어져
있으므로 추가로 세지 않는다.

## 5. 반복 종료 후 보고

완료했을 때와 `NEEDS_HUMAN`으로 멈췄을 때 모두 해당 Issue에 아래 형식으로 코멘트를 남긴다.

### 완료 코멘트

```
## <✅ 완료 | 🛑 NEEDS_HUMAN> — N차 시도

- 상태: <완료 | NEEDS_HUMAN>
- 검증: <PASS | FAIL | 중단>
- 종료 조건:
  - [x/ ] <종료 조건 1> — <확인 결과>
  - [x/ ] <종료 조건 2> — <확인 결과>
- 작업 내용: <이번 시도에서 변경하거나 확인한 내용>
- 판단 필요: <없음 | 사람이 판단해야 할 내용>
```

`NEEDS_HUMAN`으로 멈춘 뒤에는 판단을 받기 전까지 그 사유에 의존하는 변경을 하지 않는다
(`00-ssot.md §4`). 최대 횟수 소진의 경우 마지막 실패 상태를 그대로 두고 추가로 재구현하지
않는다.

### 시도 횟수 초기화 코멘트

사람 검증 반려로 시도 횟수를 0으로 되돌릴 때 해당 Issue에 남긴다 (§6.3).

```
## 🔄 시도 횟수 초기화 — 사람 검증 반려

- 반려 사유: <무엇이 어긋났는가>
- 종료 조건: <걸린 종료 조건 | 종료 조건 밖 — 갱신 필요>
- 이전 시도: N차까지 (초기화)
- 다음: 1차 시도부터 다시 센다
```

### PR 코멘트

PR을 연 뒤에 내려진 판정은 그 PR에 남긴다. Issue 코멘트를 대신하지 않는다. 사유와 다음 행동만
짧게 적고, 같은 내용을 두 벌 적지 않는다.

| 시점 | 남기는 사람 | 내용 |
|---|---|---|
| 사람 검증 통과 | 검증한 사람 | 확인한 항목과 머지해도 된다는 판정 |
| 사람 검증 반려 | 반려한 사람 | 반려 사유와 어느 종료 조건에 걸리는지 |
| PR 단계에서 `NEEDS_HUMAN` | AI | 정지 사유와 Issue 코멘트의 위치 |

## 6. PR·CI 진입과 복귀

로컬 판정이 끝난 변경을 언제 PR로 올리고, CI 결과를 받아 루프의 어디로 돌아오는지를 정한다.

CI가 무엇을 검사하는지는 여기서 정하지 않는다. `.github/workflows/verify.yml`은 로컬
`npm run verify`와 같은 것을 그대로 돌린다. 검사 내용의 원본은 `02`다.

### 6.1 진입 조건

다음 셋을 모두 만족한 시점에만 PR로 넘어간다.

1. 마지막 시도의 `npm run verify`가 PASS
2. Issue의 종료 조건이 전부 참
3. §5의 완료 코멘트를 해당 Issue에 남겼다

`NEEDS_HUMAN`으로 멈춘 상태에서는 PR을 열지 않는다. 사람의 판단을 받아 재개하고 위 셋을 다시
만족시킨 뒤에 넘어간다.

커밋·푸시·PR 생성 자체는 사람이 요청했을 때만 한다 (`AGENTS.md §3`). 이 절은 넘어가도 되는
상태인지를 정할 뿐, 그 요청을 대신하지 않는다. 조건을 만족하면 만족했다는 사실을 보고하고
기다린다.

Issue 작업은 `main`이 아닌 작업 브랜치에서 수행한다. 브랜치 이름은
`<유형>/issue-<번호>-<요약>` 으로 짓는다. 유형은 커밋 메시지의 것과 같고(`feat` · `fix` ·
`docs` · `chore`), 요약은 영소문자와 하이픈으로 짧게 적는다 — `fix/issue-12-inventory-adjustment`.

PR은 그 작업 브랜치에서 `main`을 향해 Issue 하나당 하나 연다. 본문에는 Issue 번호와 §5 완료
코멘트의 위치를 적는다. 같은 내용을 PR 본문에 옮겨 적지 않는다.

### 6.2 CI 결과와 복귀

PR을 열면 `verify` 워크플로가 돈다. 그 결과에 따라 다음으로 간다.

```
PR (§6.1) → CI
             │
    ┌────────┴────────┐
   PASS              FAIL
    │                 │
 사람 검증        로컬에서 재현되는가?
 (§6.3)              │        │
                    예       아니오
                      │        │
              §2 FAIL 갈래   NEEDS_HUMAN (§4)
```

| CI 결과 | 처리 |
|---|---|
| PASS | 사람 검증으로 넘어간다 (`02 §5` · §6.3) |
| FAIL · 로컬 `npm run verify`에서 재현됨 | §2의 FAIL 갈래로 돌아간다 |
| FAIL · 로컬에서 재현되지 않음 | 즉시 `NEEDS_HUMAN` (§4) |

재현되는 실패로 돌아왔을 때는 §2의 FAIL 갈래를 그대로 따른다. §4의 즉시 사유에 해당하는지
먼저 보고, 아니면 최대 횟수(§3)가 남았는지 본다. 남아 있지 않으면 그 자리에서
`NEEDS_HUMAN`이다.

횟수는 PR 전후로 나뉘지 않는다. 그 Issue의 같은 카운터를 이어 센다. CI 실행 자체는 세지 않고,
복귀해서 다시 구현하고 로컬 `npm run verify`를 돌린 시점에 1회가 오른다 (§1).

로컬에서 재현되지 않는 실패는 로컬 판정자가 잡지 못하는 실패다. 무엇을 고칠지가 아니라 무엇으로
판정할지의 문제이므로 (`02`의 몫) 반복하지 않고 사람에게 넘긴다.

CI FAIL로 복귀하면 앞서 남긴 완료 코멘트는 지우지 않고 그대로 둔다. 다시 §6.1을 만족했을 때
새 시도 번호로 §5의 코멘트를 한 번 더 남긴다.

머지 뒤 `main` 푸시로 도는 CI는 이 루프의 입력이 아니다. 그 시점에 루프는 이미 끝나 있다.

### 6.3 사람 검증 결과와 복귀

사람 검증의 시점·판정자·대상은 `02 §5`가 정한다. 이 절은 그 결과를 받아 어디로 가는지만
정한다.

| 결과 | 다음 |
|---|---|
| 통과 | PR에 통과 코멘트를 남긴다 (§5). 사람이 머지하고 루프는 끝난다 |
| 반려 | PR에 반려 코멘트를 남긴다 (§5). 구현 단계로 돌아가고 시도 횟수를 0으로 초기화한다 |

기계 검증의 FAIL과 사람 검증의 반려는 다르게 다룬다. FAIL은 같은 요구를 아직 맞추지 못한
것이라 카운터를 이어 센다. 반려는 요구 자체가 달랐을 수 있다는 신호다. 앞선 시도들은 다른
요구를 향해 쓴 것이므로 남은 횟수로 세지 않고, 0부터 다시 센다 (§3).

반려 사유가 Issue 종료 조건 밖의 요구이면 종료 조건을 먼저 갱신하고 구현에 들어간다. 갱신안은
AI가 내고 사람이 확정한다 (`00-ssot.md §5`). 갱신 전에는 구현하지 않는다.

반려는 사람이 내린 판단이므로 그 자체로 §4의 `NEEDS_HUMAN`을 선언하지 않는다. 초기화한
사실은 §5의 양식으로 Issue에 남긴다.

초기화 뒤에는 1차 시도부터 다시 센다. 다시 §6.1을 만족하면 §5의 완료 코멘트를 1차 시도로
남기고 같은 PR로 돌아온다. PR을 새로 열지 않는다.

CI PASS만으로 머지하지 않는다. 사람 검증을 건너뛰는 경로는 없다.
