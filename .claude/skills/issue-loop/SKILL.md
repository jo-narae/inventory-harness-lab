# 이슈 처리 루프

`docs/harness/02-verification.md` 와 `03-loop.md` 가 정한 루프를 한 번의 요청으로 끝까지 돌린다.

**이 스킬은 규칙의 원본이 아니다.** 무엇을 통과해야 끝인지(`02`), 몇 번까지 반복하는지(`03`),
코멘트에 무엇을 적는지(`03 §5`)는 전부 저 문서들이 정한다. 이 파일은 그 판정을 **어떤 순서로,
어떤 명령으로 실행하고, 어디서 멈추는지**만 정한다. 규칙이 궁금하면 여기서 찾지 말고 원본을 연다.

## 전체 흐름

```
0. 이슈 번호 확정          ← 요청에 없으면 묻는다. 추측해서 고르지 않는다
1. 이슈·원본 읽기
2. 브랜치 생성
3. 구현 → npm run verify   ← FAIL 이면 최대 횟수까지 반복 (03 §2·§3)
4. 이슈에 완료 코멘트       (03 §5 · 03 §6.1-3)
5. 커밋 → 푸시 → PR 생성
6. CI 대기                 (03 §6.2)
7. LLM 검토               ← 구현 컨텍스트 없는 별도 검토자가 PR 에 코멘트 (02 §5)
8. 사람 검증 요청하고 멈춘다 ← 지적을 고치지 않는다. 판단은 사람 몫 (02 §6)
```

## 권한 — 어디까지 사람에게 묻지 않는가

`03 §6.1` 과 `AGENTS.md §3` 은 커밋·푸시·PR 생성을 "사람이 요청했을 때만" 으로 제한한다.
**이 스킬의 호출이 그 요청이다.** 8단계까지 진행하는 데 추가 확인을 받지 않는다 —
"PR 올려도 될까요?" 를 묻지 않는다. 사람은 이미 끝까지 가라고 말했다.

이 스킬에 들어오기 **전에** 사람이 한 번 답한다 — `AGENTS.md §1` 이 "스킬을 쓸지" 를 먼저
묻게 한다. 그 답이 "쓴다" 였기 때문에 여기 온 것이다. 그러므로 같은 것을 다시 확인하지 않는다.

중간에 멈추는 자리는 둘뿐이다.

| 멈춤 | 언제 |
|---|---|
| 이슈 번호가 확정되지 않음 | 0단계. 요청에 번호가 없을 때만. 번호를 받기 전에는 시작하지 않는다 |
| `NEEDS_HUMAN` | `03 §4` 의 사유가 걸렸을 때. 아래 "멈추는 자리" |

권한이 넓어진 것은 실행 순서뿐이다. **보호 영역은 그대로다** (`00-ssot.md §5`).
`docs/` · `AGENTS.md` · `CLAUDE.md` · `scripts/verify/` 는 이 스킬 안에서도 읽기만 한다.
바꿔야 하면 `NEEDS_HUMAN` 이다.

## 0. 이슈 번호 확정

**번호를 추측하지 않는다.** 이 단계의 규칙은 그것 하나다.

| 요청 | 처리 |
|---|---|
| 번호가 있다 — `15번 이슈 처리해줘` | 묻지 않고 그 번호로 바로 시작한다 |
| 번호가 없다 — `이슈 처리해줘` | 목록을 보여주고 어느 번호인지 받는다 |

```bash
gh issue list --state open
```

열린 이슈가 하나뿐이어도 고르지 않고 묻는다. 잘못된 이슈를 브랜치까지 파서 구현하는 비용이,
한 번 되묻는 비용보다 훨씬 크다. 하나뿐이라는 것은 그것이 지금 처리할 이슈라는 뜻이 아니다.

번호를 받고 나면 이 스킬은 8단계까지 다시 묻지 않는다 (위 "권한").

## 1. 이슈와 원본 읽기

```bash
gh issue view <N>
```

이슈 폼의 6칸에서 다음을 뽑는다.

| 칸 | 뽑을 것 | 쓰는 곳 |
|---|---|---|
| 3. 종료 조건 | 참·거짓을 확인할 문장들 | 4단계 완료 코멘트의 체크 항목 |
| 4. 기계 검증 | Issue 전용 테스트 경로 | 3단계 구현 |
| 5. 건드리면 안 되는 것 | 변경 경계 | 구현 내내 |
| 6. 최대 횟수 | 1·2·3·5 중 하나 | 3단계 반복 상한 |

**6번 칸이 없으면**(폼을 거치지 않은 이슈) 폼 기본값인 **3회**로 본다 (`03 §3`).
묻지 않는다 — 원본이 정해 둔 값이 있으므로 물을 것이 없다.

그다음 이슈가 닿는 원본을 읽는다. **전부 읽지 않는다** — `AGENTS.md §0` 의 읽기 원칙대로
`grep -n "^#" <파일>` 로 목차를 잡고 필요한 절만 `sed -n 'A,Bp'` 로 연다.
재고 규칙은 `docs/01-requirements.md`, 구조는 `docs/06-architecture.md` 다.

읽는 동안 Issue ↔ 원본, 원본 ↔ 원본이 어긋나 있는 것을 발견하면 그 자리에서 `NEEDS_HUMAN` 이다
(`00-ssot.md §4`). 어느 쪽이 옳아 보여도 고르지 않는다.

## 2. 브랜치 생성

`main` 에서, 최신 상태에서 딴다. Protect 단계가 `origin/main` 과의 merge-base 를 기준으로
변경 파일을 잡으므로(`scripts/verify/check-protected.ts`), fetch 를 건너뛰면 엉뚱한 파일이
변경으로 잡힌다.

```bash
git switch main && git fetch origin main && git merge --ff-only origin/main
git switch -c <유형>/issue-<N>-<요약>
```

- 유형: `feat` · `fix` · `docs` · `chore` — 커밋 메시지의 것과 같다
- 요약: 영소문자와 하이픈으로 짧게. 예 `fix/issue-12-inventory-adjustment`

**추적 중인 파일에 커밋되지 않은 수정이 있으면** 멈추고 사람에게 알린다. 남의 진행 중인
변경 위에 얹어 커밋하지 않기 위해서다 (`git status --short` 의 `M`·`A`·`D`).

추적되지 않는 파일(`??`)은 멈출 이유가 아니다. `.claude/settings.local.json` 처럼 사람의
로컬 설정이 흔히 여기 잡히는데, 그것은 남이 하던 작업이 아니다. 대신 커밋할 때 `git add .`
를 쓰지 않고 이번에 고친 파일만 명시적으로 스테이징한다 — 그러면 무엇이 들어갈지가 항상
눈에 보인다.

## 3. 구현 → `npm run verify`

한 번의 시도(iteration)는 **구현 + `npm run verify` 1회**다 (`03 §1`). 검증을 돌린 시점에
횟수가 오른다. PASS 든 FAIL 든 같다.

```bash
npm run verify
```

단계를 낱개로 돌리는 것은 개발 중 확인일 뿐 판정이 아니다 (`02 §2`). 빠르게 확인하려고
`npm test` 만 돌린 결과를 검증 결과로 보고하지 않는다.

이 명령은 먼저 실패한 단계에서 멈추므로 한 번의 실행이 보고하는 실패는 **언제나 하나다**.
뒤 단계가 통과할지는 그 실행으로 알 수 없다.

FAIL 이면:

1. `03 §4` 의 즉시 사유에 해당하는가 → 해당하면 곧바로 `NEEDS_HUMAN`
2. 아니면 최대 횟수가 남았는가 → 남았으면 원인을 분석하고 재구현 후 다시 `npm run verify`
3. 남지 않았으면 `NEEDS_HUMAN`

같은 단계가 같은 원인으로 다시 실패해도 횟수가 남았으면 계속한다 — 원인이 같다는 것 자체는
멈추는 근거가 아니다 (`03 §2`).

구현 중 지킬 것 (`AGENTS.md §3`):

- 재고 수량 변경은 `applyMovement()` 하나로만. 새 통로를 만들지 않는다 (`06 §4.1`)
- 유통기한은 `lib/date.ts` 의 `dateOnly()` 를 통과시킨다
- 시드 상품은 배열 **뒤에만** 붙인다 — 중간에 끼우면 ID 가 밀린다
- 이 Issue 전용 테스트는 `tests/issues/issue-<N>-<기능명>.test.ts` 에. 다른 Issue 의 테스트는
  고치지 않는다 (`02 §4`)
- 종료 조건에 대응하는 테스트가 없으면 무엇으로 판정할지 **이슈에 먼저 코멘트로 적고** 돌린다

빌드가 앞선 실패의 `.next` 캐시 때문에 죽는 일이 있었다 (Issue #12 2차 시도). Build 단계가
코드와 무관해 보이는 내부 오류로 실패하면 `rm -rf .next` 후 재실행을 한 번 시도해 볼 만하다 —
그것도 1회 시도로 센다.

## 4. 이슈에 완료 코멘트

PASS 하고 종료 조건이 전부 참이면 이슈에 코멘트를 남긴다. 이것이 PR 진입 조건의 셋째다
(`03 §6.1`).

양식은 `03 §5` 의 **완료 코멘트**다. 이 파일에 옮겨 적지 않았다 — 두 벌이 되면 어느 쪽이
맞는지 알 수 없어진다. 쓰기 전에 열어서 그대로 따른다.

```bash
sed -n '/^### 완료 코멘트/,/^### 시도 횟수 초기화/p' docs/harness/03-loop.md
gh issue comment <N> --body-file <파일>
```

쓸 때 지킬 것:

- **종료 조건 줄마다 "무엇으로 확인했는지"를 적는다.** `[x] 조건 1 — 통과` 는 아무것도
  말해주지 않는다. 어떤 값이 어떻게 나왔고 어느 테스트가 판정했는지를 적는다
- **작업 내용은 시도별로 적는다.** 1차에 뭘 했고 왜 실패했고 2차에 뭘 고쳤는지가 남아야
  나중에 사람이 판단할 수 있다
- **판단 필요 칸을 비우지 않는다.** 없으면 `없음` 이라고 적는다. 원본이 정하지 않아
  이번에 임의로 정한 것이 있으면 전부 여기 적는다

`NEEDS_HUMAN` 으로 멈춘 경우에도 같은 양식으로 남기고 **여기서 끝난다** — 5단계로 가지 않는다.

## 5. 커밋 · 푸시 · PR

`03 §6.1` 의 셋을 모두 만족한 뒤에만 온다. 커밋 메시지는 이 저장소의 형태를 따른다
(`git log` 로 확인).

```
<유형>(<범위>): <한 줄 요약>

<왜 이렇게 했는지. 무엇을 바꿨는지가 아니라 무엇이 문제였는지부터>

- <파일·절>  <바뀐 것>

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

보호 경로를 건드렸다면 이 자리에 `Approved-Protected: <경로>` 트레일러가 필요한데,
**그 승인을 스스로 만들지 않는다.** 보호 경로 변경이 필요한 상황은 3단계에서 이미
`NEEDS_HUMAN` 으로 멈췄어야 한다.

```bash
git push -u origin <브랜치>
gh pr create --base main --title "<커밋 제목과 같게>" --body "..."
```

PR 본문에는 **Issue 번호와 완료 코멘트의 위치만** 적는다. 완료 코멘트의 내용을 옮겨 적지
않는다 (`03 §6.1`). 예:

```
#<N> 의 구현.

종료 조건 대조와 시도별 작업 내용은 Issue #<N> 의 완료 코멘트에 있다.
```

## 6. CI 대기

PR 을 열면 `verify` 워크플로가 돈다. **CI 가 PASS 한 뒤에야 LLM 검토를 돌린다**
(`02 §5` · `03 §6.2`). 기다린다.

```bash
gh pr checks --watch
```

| CI 결과 | 다음 |
|---|---|
| PASS | 7단계로 |
| FAIL · 로컬 `npm run verify` 에서 재현됨 | 3단계 FAIL 갈래로 돌아간다. 같은 카운터를 이어 센다 |
| FAIL · 로컬에서 재현 안 됨 | 즉시 `NEEDS_HUMAN` (`03 §4`) |

CI 실행 자체는 시도로 세지 않는다. 돌아와서 다시 구현하고 로컬 `npm run verify` 를 돌린
시점에 1회가 오른다.

CI FAIL 로 돌아가도 앞서 남긴 완료 코멘트는 지우지 않는다. 다시 조건을 만족했을 때 **새 시도
번호로** 한 번 더 남긴다. PR 도 새로 열지 않는다.

## 7. LLM 검토 — 분리된 검토자에게 맡긴다

CI 가 PASS 한 뒤, 사람 검증을 요청하기 전에 도는 층이다 (`02 §5`). **경고이지 판정이 아니다**
(`02 §3`) — 지적이 있어도 사람 검증으로 넘어간다.

### 왜 구현한 쪽이 직접 하지 않는가

`02 §5` 는 이 층의 한계를 스스로 적어 두었다 — *"자기 변경을 자기가 훑은 것이므로 통과
판정으로 읽지 않는다."* 구현한 컨텍스트에는 "왜 이렇게 했는지"가 이미 들어 있어서, 밖에서
보면 이상한 선택이 안에서는 자연스러워 보인다. 그 컨텍스트를 지운 채 diff 와 원본만 보는
쪽이 이 층이 잡으라는 것을 실제로 잡는다.

그래서 **검토는 구현 컨텍스트가 없는 별도 에이전트에게 맡긴다.** `02 §5` 의 실행자는
"AI. 로컬에서 검토하고 결과를 그 PR 에 코멘트로 남긴다" 이고 어느 AI 인지는 열려 있으므로,
이것은 규칙 변경이 아니라 실행 방법이다.

### 어떻게

3~6단계를 돈 에이전트는 **검토를 직접 하지 않는다.** 서브에이전트를 하나 띄우고,
아래 세 가지만 준다.

| 준다 | 주지 않는다 |
|---|---|
| PR 번호 · Issue 번호 · 브랜치 이름 | 구현 과정의 판단·시행착오·"왜 이렇게 했는지" |
| `git diff origin/main...<브랜치>` 를 직접 읽으라는 지시 | 완료 코멘트의 작업 내용·판단 필요 |
| 원본 위치 (`02 §5` · `03 §5` · Issue 종료 조건 · `01` · `06`) | 어디를 봐 달라는 힌트, 어디는 괜찮다는 안내 |

오른쪽 칸이 이 단계의 핵심이다. 하나라도 흘리면 분리한 의미가 없어진다. 특히 **"여기는 이미
검토했다"·"이건 의도한 것이다" 를 미리 알려주지 않는다** — 그 말이 곧 검토자가 볼 자리를
좁히는 일이다.

검토자에게 줄 지시의 뼈대:

```
작업 디렉터리: <저장소 경로>
PR #<번호> (Issue #<N>, 브랜치 <브랜치>) 를 `02 §5` 의 LLM 검토로 훑어라.
너는 이 구현에 참여하지 않았다. diff 와 원본만 읽고 판단해라.

1. `git diff origin/main...<브랜치>` 로 변경 전체를 읽어라
2. `gh issue view <N>` 으로 종료 조건을 읽어라
3. `sed -n '/^## 5. LLM 검토/,/^---/p' docs/harness/02-verification.md` 로
   무엇을 보고 무엇을 보지 않는지 확인해라
4. 지적의 근거가 필요하면 `docs/01-requirements.md` · `docs/06-architecture.md` 에서
   해당 절만 열어라
5. `sed -n '/^### LLM 검토 코멘트/,/^### 반려 코멘트/p' docs/harness/03-loop.md`
   의 양식 그대로 코멘트를 작성해 `gh pr comment <번호> --body-file <파일>` 로 직접 남겨라

코드를 고치지 마라. 커밋·푸시하지 마라. 코멘트만 남긴다.
```

**검토자가 코멘트를 직접 남긴다.** 구현한 에이전트가 받아서 옮겨 적지 않는다 — 그 사이에
표현이 부드러워지는 것을 막을 방법이 없다. 구현한 쪽은 코멘트가 실제로 올라갔는지만 확인한다.

```bash
gh pr view <PR번호> --comments | grep -c "LLM 검토"
```

`- 대상:` 칸에 검토 범위와 함께 **구현 컨텍스트와 분리된 검토자가 읽었다는 사실**을 적는다.
사람이 이 코멘트의 무게를 가늠하는 데 필요한 정보다. 양식에 칸을 새로 만들지는 않는다.

### 검토자가 지킬 것

- **본다** — 구현이 종료 조건·원본의 **의도**와 어긋나는가 · 새로 생긴 규칙 중 **판정하는 것이
  없는 자리**가 생겼는가 · 놓친 엣지 케이스 · 뒤에 유지보수를 어렵게 할 구조
- **보지 않는다** — 타입·린트·경로 규칙·불변식. 기계 검증이 이미 판정한 것을 다시 적지 않는다
- **지적마다 `파일:줄` 과 근거를 붙인다.** 근거는 원본의 위치이거나 종료 조건이다.
  근거를 댈 수 없는 것은 취향이지 지적이 아니다
- **지적이 없으면 `없음` 이라고 적는다.** 비워 두지 않는다
- **`판정이 비는 자리` 를 성실히 채운다.** 이 층이 존재하는 이유의 절반이 여기다 —
  기계 검증이 통과했는데 아무도 판정하지 않는 규칙이 새로 생겼다면 그것이 이 칸에 들어간다

### 검토가 끝난 뒤

**지적을 고치지 않는다.** 경고이지 판정이 아니고, 처리 여부는 사람이 정한다 (`02 §5`).
지적을 보고 곧바로 고치면 사람이 판단할 자리를 없애는 것이다. 고치기로 하는 결정이 나면
그것은 사람 검증 반려와 같은 경로로 돌아온다 (`03 §6.3`).

검토를 돌리지 못했으면 **돌리지 못했다는 사실을 제목 줄에 적는다.** 실행하지 않은 것을
지적이 없는 것으로 보고하지 않는다 (`02 §3`). 서브에이전트를 띄울 수 없는 환경이면 그
사실을 알리고, 구현 컨텍스트를 최대한 배제한 채 diff 와 원본만으로 검토한 뒤 그 조건도
`- 대상:` 칸에 적는다.

검토 중 원본끼리 또는 Issue 와 원본이 어긋난 것을 발견하면 그것은 검토 지적이 아니라
**충돌**이다. `NEEDS_HUMAN` 을 선언한다 (`02 §5`).

## 8. 사람 검증 요청하고 멈춘다

여기가 이 스킬의 끝이다. **머지하지 않는다.** CI PASS 도, 지적 없는 LLM 검토도 머지 근거가
아니다 (`03 §6.3`).

사람에게 다음을 보고한다.

- PR 링크
- 로컬 검증 결과와 몇 차 시도였는지
- CI 결과
- LLM 검토 지적 건수
- **이번 변경이 닿은 화면·흐름** — 사람이 `07 §2` 체크리스트 B~D 중 무엇을 볼지 정하는 입력

사람이 반려하면 `03 §6.3` 이다 — 시도 횟수가 0으로 초기화되고 3단계로 돌아간다.
그때 재구현의 입력은 **Issue 종료 조건과 반려 코멘트 둘뿐**이다. PR 대화의 다른 줄이나
앞선 완료 코멘트를 입력으로 삼지 않는다. 반려 코멘트가 읽히지 않으면 추측하지 말고 그 PR 에
되묻고 기다린다.

---

## 멈추는 자리 — `NEEDS_HUMAN`

`03 §4` 가 정한다. 아래 다섯 중 하나가 걸리면 그 자리에서 멈추고, `03 §5` 양식으로 이슈에
남긴 뒤 사람의 판단을 기다린다. **판단을 받기 전까지 그 사유에 의존하는 변경을 하지 않는다.**

| 사유 | 언제 |
|---|---|
| Protect 단계 실패 — 보호 경로 변경이 필요해짐 | 즉시 |
| Issue ↔ 원본 · 원본 ↔ 원본 충돌 | 즉시. `00-ssot.md §4` 의 4항목 형식으로 |
| 구현 중 Issue 범위를 벗어나는 변경이 필요해짐 | 즉시 |
| CI 실패가 로컬에서 재현되지 않음 | 즉시 |
| 최대 시도 횟수 소진 | 횟수를 다 쓴 뒤 |

앞의 넷은 남은 횟수와 무관하다. 어느 시점에 걸려도 그 시도는 1회를 소진한 것으로 센다.

멈추는 것은 실패가 아니다. 원본이 정하지 않은 것을 추측으로 채우고 넘어가는 것이 실패다.
