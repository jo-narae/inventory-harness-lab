## 1. 출발점 — 있는 것과 없는 것

입력은 질문이었다. *"사람이 PR 에 반려 코멘트를 남기면 AI 가 그 코멘트를 읽고 의도를 파악해
다시 구현하는 흐름이 있나. Issue 에 재진입 기록을 남기고 시도 횟수는 1차부터 다시 세야 할 것
같은데 지금 그렇게 되어 있나."*

절반은 이미 있었다. 감사 결과를 먼저 보고하고, 없는 것만 골라 채웠다.

| 물은 것 | 상태 | 근거 |
|---|---|---|
| 반려하면 구현 단계로 돌아가나 | **있었다** | `03 §6.3` 표 |
| 시도 횟수가 0 으로 초기화되나 | **있었다** | `03 §3` · `§6.3` — 기계 FAIL 과 다르게 다루는 이유까지 |
| Issue 에 재진입 기록이 남나 | **있었다** | `03 §5` 「시도 횟수 초기화 코멘트」 |
| AI 가 반려 코멘트를 읽는다는 단계가 있나 | **없었다** | `§6.3` 은 "어디로 가는지"만 정했다. 입력은 정의된 적이 없다 |
| 반려 코멘트에 양식이 있나 | **없었다** | `03 §5` — "넷 중 이것만(LLM 검토) 양식을 정해 둔다" |
| 사유를 읽어도 뜻이 안 잡히면 | **없었다** | 추측·되묻기·정지 중 무엇인지 비어 있었다 |

없는 셋을 그대로 보고했더니 사람이 전부 채우라고 했다. `AGENTS.md §0`("원본에 없으면 정해지지
않은 것이다 — 코드에서 추측해 채우지 말고 없다고 보고한 뒤 물어라")대로 간 경로다.

## 2. 완료한 것

### `03 §5` — 반려 코멘트 양식 신설

PR 코멘트 4종 중 두 번째로 양식이 생겼다. 바로 위 LLM 검토 코멘트의 "넷 중 **이것만** 양식을
정해 둔다"도 "이것과 아래 반려 코멘트만"으로 함께 고쳤다.

```
## 🛑 반려 — 사람 검증

- 반려 사유: <무엇이 어긋났는가>
- 걸린 종료 조건: <종료 조건의 번호와 문구 | 종료 조건 밖 — 갱신 필요>
```

두 칸만 적는다. **무엇을 어떻게 고칠지는 적지 않는다** — 그것은 구현이고, Issue 범위 안에서
AI 가 정한다.

### `03 §6.3` — 재구현의 입력

> §5의 반려 코멘트가 이번 재구현의 입력이다. 다음 시도는 Issue의 종료 조건과 그 코멘트 둘만
> 놓고 시작한다. PR 대화의 다른 줄이나 앞선 시도의 완료 코멘트를 입력으로 삼지 않는다.

카운터가 0 이 되는 것과 짝을 이룬다. 앞선 시도를 횟수로 세지 않기로 했으면, 앞선 시도의
기록도 다음 시도의 입력이 아니어야 앞뒤가 맞는다.

### `03 §6.3` — 판단이 안 서면 되묻는다

> 반려 코멘트를 읽어도 무엇이 어긋났는지 정해지지 않으면 **추측해서 구현하지 않는다.** 두 칸 중
> 빈 곳이나 여러 갈래로 읽히는 곳을 그 PR 에 되묻고 답을 기다린다. 답을 받기 전에는 구현에
> 들어가지 않는다. 되묻는 것은 구현과 `npm run verify` 의 묶음이 아니므로 시도 횟수는 오르지
> 않는다 (§1). 이미 사람이 판정 중인 자리이므로 §4 의 `NEEDS_HUMAN` 을 따로 선언하지도 않는다.

### 동기화 — 없다

이번에는 다른 파일을 한 글자도 고치지 않았다. 새 절을 만들지 않았고 번호도 밀지 않았기
때문이다.

- `02 §6` 표의 「결과 기록」 칸이 이미 `03 §5` 로 라우팅하고 있다 — 양식을 `03` 에 두면 `02` 는
  그대로 유효하다
- `02 §6` 표의 「반려하면」 칸도 이미 `03 §6.3` 을 가리킨다
- `AGENTS.md §1` 라우팅 표의 `03` 행은 `PR·CI §6` 으로 이미 이 자리를 덮는다
- `00-ssot.md §2` 책임 경계도 그대로 — 반려 뒤의 복귀는 원래 `03` 의 몫이다

## 3. 어떻게 좁혀갔나 — 판단이 갈렸던 다섯 곳

1. **`02` 를 건드리지 않았다.** 사람 검증은 `02 §6` 이 소유하므로 반려 코멘트 양식도 그쪽인가
   저울질했다. 아니다 — `00-ssot.md §2` 기준으로 `02` 는 *언제 누가 무엇을 대상으로 판정하는가*
   까지고, 판정 **이후**의 코멘트 양식은 `03` 이다. `08` 이 LLM 검토를 `02 §5` / 코멘트를
   `03 §5` 로 가른 것과 같은 선이다.
2. **반려 코멘트에 해법을 적지 않기로 했다.** 사람이 "이렇게 고쳐라"를 적으면 그것이 사실상
   종료 조건이 되는데, 종료 조건의 원본은 Issue 다 (`00-ssot.md §1`). 두 칸으로 묶어 *무엇이
   어긋났는가* 와 *어느 종료 조건에 걸리는가* 만 남기면, 종료 조건 밖의 요구는 자동으로
   "갱신 필요"로 드러난다 — `§6.3` 이 이미 정해 둔 갈림길에 그대로 물린다.
3. **되묻기를 `NEEDS_HUMAN` 으로 만들지 않았다.** 정지력은 같지만 신호가 다르다.
   `NEEDS_HUMAN` 은 *사람이 자리에 없을 때* 부르는 신호이고, 반려 직후는 이미 사람이 판정
   중인 자리다. `§6.3` 에 "반려는 그 자체로 `NEEDS_HUMAN` 을 선언하지 않는다"가 이미 있어
   충돌도 났을 것이다. 대신 "답을 받기 전에는 구현에 들어가지 않는다"로 정지만 걸었다.
4. **되묻기를 시도 횟수로 세지 않았다.** `§1` 의 정의가 *구현 + 로컬 `npm run verify` 묶음*
   이므로 그대로 따랐다. LLM 검토를 세지 않은 것(`08`)과 같은 근거다. 되묻는 동안 카운터가
   오르면 사람의 답이 늦을수록 AI 의 남은 횟수가 줄어든다 — 그건 규칙이 아니라 벌칙이다.
5. **입력을 둘로 닫았다.** "PR 대화의 다른 줄이나 앞선 시도의 완료 코멘트를 입력으로 삼지
   않는다"를 명시했다. 열어 두면 반려 코멘트에 양식을 두는 뜻이 없어진다 — 어차피 대화 전체를
   읽을 거라면 두 칸을 채우는 값을 사람이 치를 이유가 없다.

나머지 단계는 마크다운 변경이라 검사하지 않는다 — `07 §4` · `08 §4` 와 같은 판단이다.

반려 갈래를 이번 변경까지 넣어 펼치면 이렇다.

```
사람 검증
   │
  반려 ── PR 코멘트 🛑 (두 칸 · 양식 `03 §5`)
   │           │
   │      Issue 코멘트 🔄 시도 횟수 초기화        [카운터 0]
   │           │
   │      두 칸이 읽히나?
   │        │        │
   │       아니오     예
   │        │        │
   │   PR 에 되묻고   걸린 종료 조건이 Issue 안인가?
   │   대기           │              │
   │  [카운터 안 오름]  예             아니오
   │        │        │              │
   │        └──→ 1차 시도 재구현   종료 조건 갱신(사람 확정) → 1차 시도
   │                 │
   │            같은 PR 로 복귀 (새로 열지 않는다)
   │
  통과 → 머지(사람) → 끝
```
