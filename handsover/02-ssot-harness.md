## 00. 원본 후보 조사

### 상황

문서가 10개인데 같은 내용이 여러 곳에 적혀 있었다. 어느 것을 믿어야 하는지 정해져 있지 않아,
문서를 고쳐도 다른 문서가 옛 내용을 계속 주장했다.

### 판단 기준

한 영역의 질문에 **끝까지 답할 수 있는 문서 하나**가 있으면 원본으로 본다.
답이 여러 문서에 쪼개져 있으면 원본이 없는 것으로 본다.

### 결과

| 영역 | 결과 |
|---|---|
| 재고 도메인 | `docs/01-requirements.md` 하나로 충분 — 기능·사유 체계·범위·완료 기준이 모두 있음 |
| 아키텍처 | `docs/06-architecture.md` 하나로 충분 — 스택·모델·핵심 로직·불변식이 모두 있음 |

## 01. SSOT 문서 — `docs/harness/00-ssot.md`

### 설계 원칙

**이 문서는 "무엇이 원본인가"만 정한다.** 내용을 여기에 복사하면 원본이 둘이 된다.
초안에는 문서 목록과 불일치 목록까지 넣었다가, 그것이 곧 사본이 되므로 걷어냈다.

### 구조

| 절 | 정하는 것 |
|---|---|
| 0. 원칙 | 원본은 하나 · 원본 우선 · 원본 먼저 수정 · 임의 결정 금지 · 표 갱신 |
| 1. 책임별 원본 | 재고 도메인 / 아키텍처 / 개별 작업 / 검증 규칙 / 구현·검증 루프 |
| 2. 책임 경계 | 각 원본이 **다루지 않는 것**까지 명시 |
| 3. 현재 없는 책임 영역 | 검증 규칙 · 구현·검증 루프 (추후 생성) |
| 4. 충돌 정책 | 02번 항목 참고 |
| 5. 보호 영역과 소유권 | 03번 항목 참고 |

개별 작업의 원본을 문서가 아니라 **GitHub Issue** 로 둔 것이 핵심이다.
문서는 "무엇이 참인가", Issue는 "지금 무엇을 하는가"를 담는다.

## 02. 에이전트 라우터 — `AGENTS.md` · `CLAUDE.md`

### 왜 라우터인가

SSOT를 정해도 에이전트가 시작할 때 문서를 전부 읽으면 의미가 없다.
`03-scenarios.md` 980줄, `06-architecture.md` 679줄이라 컨텍스트만 채우고 판단은 흐려진다.

그래서 `AGENTS.md`는 **규칙을 담지 않고 라우팅만 한다.**

| 절 | 내용 |
|---|---|
| 0. 읽기 원칙 | 전부 읽지 않는다 · 절 단위로 읽는다 · 막힐 때만 넓힌다 · 없으면 보고한다 |
| 1. 라우팅 표 | 질문 종류 → 읽을 문서 → 시작할 절 번호 (10행) |
| 2. 확장 사다리 | 해당 절 → 인접 절 → 근거 문서 → 코드·테스트 → 저장소 전체 |
| 3. 작업 규칙 | 원본 먼저 수정 · 사람 영역 직접 수정 금지 · Issue 범위 준수 |
| 4. 이 파일에 대하여 | `CLAUDE.md` 관계 · Next 관리 블록 |

`CLAUDE.md`는 `@AGENTS.md` 한 줄이다. 규칙을 두 벌 두지 않기 위해서다.

### 두 파일이 `.gitignore` 에 있었다

`docs/HANDOVER.md §4`에 "Next.js가 자동 생성하므로 이 프로젝트에서는 쓰지 않는다"고 적혀
`.gitignore` 58~59행에 등록되어 있었다. 그대로 두면 작성해도 커밋되지 않는다.

```bash
git check-ignore -v CLAUDE.md AGENTS.md   # 무시 여부와 근거 행 확인
```

두 줄을 지우고 사유 주석으로 교체했다(`c295572`).

### `next dev` 가 덧붙이는 관리 블록

`next dev`는 `AGENTS.md`에 `<!-- BEGIN:nextjs-agent-rules -->` 블록을 다시 써넣는다
(`node_modules/next/dist/server/lib/generate-agent-files.js`). 본문은 보존하고 블록만 갱신한다.
매번 미커밋 diff가 생기는 걸 막으려고 **블록을 미리 넣어 커밋**했다.

## 03. 충돌 정책과 보호 영역

### 충돌 정책 (`00-ssot.md §4`)

| 충돌 | 처리 |
|---|---|
| 참고 문서 ↔ SSOT | SSOT를 따르고 불일치를 보고한다 |
| Issue ↔ SSOT | `NEEDS_HUMAN` 선언 |
| SSOT ↔ SSOT | `NEEDS_HUMAN` 선언 |

선언만 하고 멈추면 사람이 무엇을 판단해야 할지 모른다. 그래서 보고에 담을 네 가지
(충돌 지점 · 각각의 주장 · 선택에 따른 결과 · 답할 질문 한 줄)와 대기 중 행동
(충돌 지점에 의존하는 변경만 중단, 무관한 작업은 계속)을 함께 정했다.

### 보호 영역 (`00-ssot.md §5`)

읽기 권한과 변경 권한을 분리한다. AI는 요구사항·아키텍처·하네스 규칙을 **읽기만** 한다.

여기서 기존 원칙과 충돌이 하나 드러났다. `§0-3`의 "원본을 먼저 수정한다"를 그대로 읽으면
AI가 원본을 직접 고쳐도 된다는 뜻이 된다. **"원본 변경 권한까지 주는 뜻이 아니다.
AI는 변경안을 제시하고, 승인 후 원본을 먼저 갱신한다"** 로 정리해 해소했다.

승인 절차가 매번 왕복이 되지 않도록 **"사람의 명시적인 수정 요청은 해당 변경에 대한 승인으로 본다"**
는 단서를 넣었다. 이 세션에서 하네스 문서를 직접 작성·커밋한 것도 이 단서로 정당화된다.

## 5. 재현 순서 (처음부터)

1. 문서 전체의 제목만 뽑아 어느 영역이 어디에 흩어져 있는지 본다
   `for f in docs/*.md; do echo "## $f"; grep -n "^#\{1,3\} " "$f"; done`
2. 영역마다 "이 질문에 끝까지 답하는 문서가 하나인가"를 따진다 → 원본 / 원본 없음
3. `docs/harness/00-ssot.md` 에 **원본 지정만** 적는다. 내용은 복사하지 않는다
4. `AGENTS.md` 에 질문 → 원본 라우팅 표와 확장 사다리를 적는다. `CLAUDE.md` 는 `@AGENTS.md`
5. `.gitignore` 에서 두 파일이 무시되는지 확인하고 해제한다
6. 충돌 정책(§4)과 보호 영역(§5)을 더한다 — 규칙이 지켜지려면 **라우터에도 같은 줄**을 넣는다
