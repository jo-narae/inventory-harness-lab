## 1. 출발점 — 조건이 어디에도 없었다

"PR과 CI로 넘어가는 조건이 명시되어 있나"를 확인하는 것으로 시작했다. 결과는 **없음**이었다.

| 있던 것 | 없던 것 |
|---|---|
| `.github/workflows/verify.yml` — `pull_request` 전체 + `push: main` 에서 `npm run verify` | 언제 PR로 넘어가는가 |
| `00-ssot.md §5` 승인 기록의 유효 범위 "로컬·CI" (CI의 존재를 전제) | CI FAIL이 시도 횟수에 들어가는가 |
| `AGENTS.md §3` "커밋·푸시는 요청받았을 때만 · `main`에 직접 커밋 금지" (금지 규칙) | CI 통과가 머지 게이트인가, 누가 머지하나 |
| PR #7~#11 의 관행 | `NEEDS_HUMAN` 상태에서 PR을 여는가 |

`03-loop.md`는 `§5` 완료 코멘트에서 끝나 있었고, `§6`(당시 미정 목록)에도 PR 항목이 없었다.
`00-ssot.md §3`은 "현재 모든 책임 영역에 원본이 있다"고 단언하고 있었지만, 브랜치·PR·머지는
책임 영역으로 열거되지도 않은 상태였다.

`AGENTS.md 0절 4번`("원본에 없으면 정해지지 않은 것이다")대로 없다고 보고한 뒤, 사람의 지시를
받아 채워 나갔다.

## 2. 완료한 것

### `03-loop.md §6` — PR·CI 진입과 복귀

**§6.1 진입 조건.** 셋을 모두 만족한 시점에만 PR로 넘어간다 — 마지막 시도의 `npm run verify`
PASS · Issue 종료 조건 전부 참 · `§5` 완료 코멘트를 남김. `NEEDS_HUMAN` 상태에서는 열지 않는다.

브랜치는 `main`이 아닌 `<유형>/issue-<번호>-<요약>`. 유형은 커밋 메시지와 같고(`feat` · `fix` ·
`docs` · `chore`), 요약은 영소문자·하이픈. PR #1~#11 에서 실제로 쓰던 형태를 그대로 적었다.

**§6.2 CI 결과와 복귀.**

| CI 결과 | 처리 |
|---|---|
| PASS | 사람 검증으로 넘어간다 |
| FAIL · 로컬에서 재현됨 | `§2`의 FAIL 갈래로 복귀, 카운터는 이어감 |
| FAIL · 로컬에서 재현 안 됨 | 즉시 `NEEDS_HUMAN` (`§4`에 행 추가) |

**§6.3 사람 검증 결과와 복귀.**

| 결과 | 처리 |
|---|---|
| 통과 | PR에 통과 코멘트 → 사람이 머지, 루프 종료 |
| 반려 | PR에 반려 코멘트 → 구현으로 복귀, **시도 횟수 0으로 초기화** |

### `02-verification.md` — 선언만 있고 비어 있던 칸 메우기

`§0` 범위표가 자기 몫으로 잡아 놓고 본문에 없던 네 항목을, **새 정책을 만들지 않고 이미 사실인
것만** 적어 채웠다 (51줄 → 131줄).

| 단계 중단과 건너뛰기 | `&&` 한 줄이라 먼저 실패한 데서 멈춘다 — 한 실행이 보고하는 실패는 항상 하나 |
| `§3` 게이트와 경고 | Prepare를 뺀 모든 단계가 게이트, 경고 층 없음 |

### `02 §5` — 사람 검증 층 확정

`§1` 두 층 표의 `⬜ 미정`이 `확정 (§5)`이 됐다.

| 항목 | 규칙 |
|---|---|
| 시점 | CI가 PASS한 뒤, 머지 전 |
| 판정자 | 사람. AI는 요청하고 기다린다 |
| 대상 | `07 §2` 체크리스트 B~D 중 **이번 Issue가 건드린 화면·흐름 항목만** |
| 결과 기록 | 통과·반려 모두 PR 코멘트 (`03 §5`) |

`07-plan.md §2`의 B~D는 원래 "M7 종료 시" 한 번 도는 전체 QA 체크리스트다. 유지보수 Issue마다
통째로 돌리는 것은 현실적이지 않아 **닿은 항목만** 보는 것으로 좁혔고, 닿지 않은 항목은 앞선
검증에서 이미 판정된 것으로 본다고 적었다.

### 반려 = 카운터 0, 그리고 코멘트 3종

기계 FAIL과 사람 반려를 같은 카운터로 세지 않기로 했다. FAIL은 *같은 요구를 아직 맞추지 못한
것*이라 이어 세지만, 반려는 *요구 자체가 달랐을 수 있다*는 신호이므로 앞선 시도를 남은 횟수로
세지 않는다.

| 남기는 곳 | 무엇 |
|---|---|
| Issue | 완료/`NEEDS_HUMAN` 코멘트 (기존 `§5`) |
| Issue | `🔄 시도 횟수 초기화 — 사람 검증 반려` (신설) |
| PR | PR을 연 뒤의 판정만 — 통과·반려·PR 단계 정지. 사유와 다음 행동만 짧게 |

## 3. 어떻게 좁혀갔나 — 판단이 갈렸던 다섯 곳

1. **커밋·푸시 권한.** `AGENTS.md §3`("요청받았을 때만")과 충돌하지 않게, `§6.1`은 *넘어가도
   되는 상태인지*만 판정하고 요청을 대신하지 않는 것으로 썼다. 규칙 둘이 어긋나면
   SSOT ↔ SSOT 충돌이 되어 `NEEDS_HUMAN` 감이다.
2. **CI를 시도로 세지 않은 이유.** `§1`이 세는 것은 "구현 + 로컬 `verify` 1회"의 묶음이다. CI는
   그 묶음이 아니다. 복귀해서 재구현하고 로컬 검증을 돌린 시점에 1회가 오른다.
3. **로컬 재현 불가를 즉시 정지로 둔 이유.** 로컬 판정자가 잡지 못하는 실패는 *무엇을 고칠지*가
   아니라 *무엇으로 판정할지*의 문제이고, 그것은 `02`(사람 승인 영역)의 몫이다.
4. **범위 밖 요구에서 `NEEDS_HUMAN`을 뺀 것.** 처음에는 "반려 사유가 종료 조건 밖이면
   `NEEDS_HUMAN`"으로 썼다가 지웠다. 반려는 이미 사람이 내린 판단이라 사람을 부르는 신호를 또
   올리는 것이 겹친다. 대신 **종료 조건을 먼저 갱신하고 구현에 들어간다**(갱신안은 AI, 확정은
   사람)로 바꿔 범위 규율만 남겼다.
5. **`§3` 게이트 문장에서 개수를 뺀 것.** "지금 여덟 단계는 모두 게이트"는 단계가 늘거나 줄면
   같이 고쳐야 한다. "Prepare를 제외하고 `npm run verify`에 포함된 모든 검증 단계는 게이트다"로
   바꿔 개수에 묶이지 않게 했다.

`npm run verify`는 이번 세션에서 돌리지 않았다 — 전부 마크다운 변경이라 어느 단계도 검사하지
않는다 (`03-verify.md §9` · `06-loop-init.md §3`의 선례와 동일).

확정된 전체 흐름은 다음과 같다.

```
Issue 확인 → 작업 브랜치 → 구현 → npm run verify   [실행 종료 시 시도 +1]
                              ↑         │
                              └─ 재구현 ─┤ FAIL → 즉시 사유? → 최대 횟수? → NEEDS_HUMAN
                              ↑         │
                              │        PASS → 종료 조건 전부 참 → 완료 코멘트(Issue)
                              │         │
                              │        PR 진입 보고 → (사람 요청) 커밋·푸시·PR
                              │         │
                              │        CI ─ FAIL·재현됨 ──→ 복귀 [카운터 이어감]
                              │         │  └ FAIL·재현안됨 → NEEDS_HUMAN
                              │        PASS
                              │         │
                              │      사람 검증 ─ 반려 → 복귀 [카운터 0] + 코멘트 2곳
                              └──────────┘
                                       통과 → PR 통과 코멘트 → 머지(사람) → 끝
```
