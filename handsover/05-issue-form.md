## 1. 완료한 것

### 여섯 칸짜리 Issue Form

`.github/ISSUE_TEMPLATE/maintenance.yml` (103줄). 여섯 칸 모두 `required: true` 다.

| # | 항목 | 묻는 것 | 타입 |
|---|---|---|---|
| 1 | 배경 | 왜 필요한가 | textarea |
| 2 | 변경할 내용 | 무엇을 수정하는가 | textarea |
| 3 | 종료 조건 | 무엇이 참이면 완료인가 | textarea |
| 4 | 기계 검증 | 어떤 테스트가 판정하는가 | textarea |
| 5 | 건드리면 안 되는 것 | 변경 경계는 어디인가 | textarea |
| 6 | 구현 루프 최대 횟수 | 몇 번까지 재시도하는가 | dropdown |

머리말은 이 Issue 가 개별 작업의 원본임(`§1`)과, 도메인·아키텍처 결정이 바뀌면 Issue 가 아니라
원본을 먼저 갱신한다는 것(`§0`)을 적어 라우팅을 폼 안에서 끝낸다.

### 세 칸은 서식이 아니라 규약이다

나머지 셋과 달리, 아래 세 칸은 "무엇을 적는가" 가 아니라 **"무엇을 적으면 안 되는가"** 까지 정한다.
판단이 갈리던 자리이기 때문이다.

**3. 종료 조건 — 실행해서 참·거짓을 확인할 수 있게.** 기준일·수치·기대 결과를 문장 안에 넣는다.
되는 예와 안 되는 예를 칸 옆에 함께 둔다.

```
되는 예
- 만료 로트 6개 폐기 시 OWN -6, DISPOSAL +6이 된다.
- 폐기 전후 모든 거점의 Lot.quantity 합계가 동일하다.

안 되는 예
- 폐기 기능이 정상적으로 동작한다. → 누가 "정상"을 판정하나
- 조회 함수가 대상 로트를 정확히 반환한다. → 입력도 기대값도 없다
```

안 되는 예에 "왜 안 되는지"를 붙인 게 핵심이다. 예시만 있으면 흉내를 내고, 이유가 있어야 새 문장을 쓴다.

**4. 기계 검증 — Issue 전용 테스트의 경로를 정했다.**

```
tests/issues/issue-{Issue 번호}-{기능명}.test.ts
```

종료 조건마다 대응하는 테스트가 있어야 한다. 대응이 없는 종료 조건은 완료를 판정할 수 없다.
`vitest.config.ts` 의 `include` 가 이미 `tests/**/*.test.ts` 라 **설정을 건드리지 않아도**
`npm test` 에 잡힌다. 임시 파일을 넣고 `npx vitest run issue-0` 으로 확인한 뒤 지웠다.

```text
Test Files  1 passed (1)
      Tests  1 passed (1)
```

**6. 구현 루프 최대 횟수 — 1·2·3·5회, 기본 3회.**
정한 횟수 안에 검증을 통과하지 못하면 AI 가 계속 반복하지 않고 멈춰 사람에게 넘긴다.

### 5번 칸의 기본값이 보호 영역을 그대로 옮겨온다

`00-ssot.md §5` 의 보호 경로를 폼 기본값으로 미리 적어두었다. 이슈 작성자가 매번 떠올리지 않아도
경계가 기본으로 붙는다.

```
- `docs/01-requirements.md` · `docs/06-architecture.md` — 읽기만 한다
- `docs/harness/` · `AGENTS.md` · `CLAUDE.md` — 읽기만 한다
- `tests/issues/` 의 다른 Issue 테스트와 `tests/` 최상위 기존 테스트 — 고치지 않는다
- `applyMovement()` 외의 재고 수량 변경 통로를 새로 만들지 않는다 (`06 §4.1`)
- 시드 상품은 배열 뒤에만 붙인다 (`handsover/01 §6`)
```

### CI 트리거를 되돌렸다

`.github/workflows/verify.yml` 의 `on:` 을 PR 중심으로 바꿨다.

```yaml
on:
  pull_request:
  push:
    branches: [main]   # 이전: ['**'] + workflow_dispatch
```

`04-ci.md §1` 에서 모든 브랜치 푸시로 넓혔던 것을 되돌린 것이다. **뒤집은 이유는 3절에 적었다.**

## 2. 어떻게 좁혀갔나

처음 만든 초안은 여섯 칸을 다 갖췄지만 안내가 추상적이었다. 다듬은 순서가 그대로 기록이 된다.

| 회차 | 무엇이 문제였나 | 어떻게 바꿨나 |
|---|---|---|
| 1 | 종료 조건이 "눈으로 확인할 수 있게" 였다 | "실행해서 참·거짓을 가릴 수 있게" + 되는 예·안 되는 예 |
| 2 | 기계 검증이 "어떤 테스트" 라고만 했다 | 파일 경로 규약 `tests/issues/issue-{번호}-{기능명}.test.ts` 로 고정 |
| 3 | 구현 루프가 횟수만 있고 멈춤이 없었다 | 못 통과하면 멈추고 사람에게 넘긴다를 문장으로 |
| 4 | 기본값이 2회였다 | 3회 |

두 번째와 세 번째가 이 폼의 값어치다. **"어떤 테스트가 판정하는가" 는 파일 이름이 정해져야 답이 되고,
"몇 번까지" 는 다 쓴 다음에 무엇을 하는지가 정해져야 답이 된다.**

초안에는 예시 경로를 `src/lib/inventory/fefo.ts` · `src/app/(app)/lots/page.tsx` 로 적었는데
둘 다 이 저장소에 없는 경로였다. 실제 경로(`src/lib/fefo.ts` · `src/app/products/[id]/page.tsx`)로
고쳤다. **폼의 예시도 코드와 어긋나면 잘못된 안내가 된다.**

| 항목 | 상태 |
|---|---|
| 브랜치 | `chore/issue-form-maintenance` (origin/main 기준) |
| 커밋 | `cc47368` Issue Form · `1f3a587` CI 트리거 되돌리기 · `2771ca0` 이 문서 |
| PR | #5 열림 |
| CI | 되돌리기 직전 PR run 통과 (1m16s) |
| 워킹 트리 | 깨끗 |

직전 브랜치 `docs/handsover-ci` 는 이미 `main` 에 병합된 상태였다. 그래서 그 위에 얹지 않고
`origin/main` 에서 새로 땄다.

`.github/` 는 보호 영역이 아니므로(`00-ssot.md §5`) `Approved-Protected:` 트레일러는 붙이지 않았다.

### 빨간 줄 하나가 트리거를 되돌리게 했다

이 PR 을 푸시하자 `gh pr checks 5` 에 `fail` 이 하나 떴다. 사유는 실패가 아니라 취소였다.

```text
Canceling since a higher priority waiting request for verify-chore/issue-form-maintenance exists
```

`04-ci.md §1` 이 만든 구조 그대로다. 푸시 트리거가 `['**']` 라 브랜치에 푸시하면 push run 이 뜨고,
PR 이 열려 있으면 pull_request run 이 또 뜬다. concurrency 그룹이 둘을 같은 이름으로 묶으므로
먼저 뜬 push run 이 취소된다. **동작 자체는 설계대로였다.** 문제는 남는 그림이다.

| | 이전 (`['**']`) | 지금 (`[main]`) |
|---|---|---|
| PR 브랜치에 푸시 | push run 취소 + PR run 통과 → **체크에 빨간 줄이 남는다** | PR run 하나만 |
| PR 없는 브랜치에 푸시 | 검증한다 | 검증하지 않는다 |
| 수동 실행 | `workflow_dispatch` 가능 | 없다 |

**빨간 줄이 "취소"인지 "실패"인지 매번 열어봐야 하는 비용이, PR 전에 브랜치를 검증해서 얻는
이득보다 컸다.** 그래서 `on:` 을 `pull_request` + `push: [main]` 으로 되돌렸다. 두 이벤트가 겹치지
않으므로 취소가 생기지 않는다.

**`04-ci.md §1` 의 "CI 를 모든 브랜치로" 는 이 세션에서 뒤집혔다.** 그 문서를 현재 상태로 읽지 않는다
(`AGENTS.md §1` — 핸드오버는 기록일 뿐이다). concurrency 그룹(`head_ref || ref_name`)은 그대로 둔다.
같은 PR 브랜치에 연속으로 푸시할 때 앞 run 을 접는 역할은 여전히 유효하다.

## 4. 주의사항

**`dropdown.default` 는 값이 아니라 0부터 세는 인덱스다.** `0=1회, 1=2회, 2=3회, 3=5회` 라
기본값 3회는 `default: 2` 로 적힌다. **옵션 순서를 바꾸면 이 숫자도 같이 고쳐야 한다.**
잘못 적어도 YAML 파싱은 통과하므로 검사에 걸리지 않는다.

**폼은 서식이지 강제가 아니다.** 필수 칸은 이슈를 *만들 때* 만 강제된다. 만든 뒤 본문을 비워도
막지 않고, 빈 이슈(blank issue)로 여는 길도 열려 있다. 폼을 유일한 입구로 만들려면
`.github/ISSUE_TEMPLATE/config.yml` 에 `blank_issues_enabled: false` 를 둔다. 운영 정책이라 정하지 않았다.

**`labels:` 는 넣지 않았다.** 저장소에 `maintenance` 라벨이 없다. 없는 라벨을 폼에 적으면 적용되지
않고 조용히 무시된다. 라벨을 먼저 만들고 폼에 추가하는 순서로 간다.

**`tests/issues/` 디렉터리는 아직 없다.** 경로 규약만 정했고 첫 Issue 가 만들면서 생긴다.
빈 디렉터리는 git 이 추적하지 않으므로 미리 만들어 커밋할 수도 없다.

**커밋 메시지와 PR #5 본문이 지금 폼보다 자세하다.** 커밋 시점 이후 6번 칸의 안내를 한 줄로
줄였는데(멈춤 보고 4항목·재시도 정의를 덜어냄), 커밋 메시지와 PR 본문에는 그 내용이 남아 있다.
**병합 전에 PR 본문을 현재 폼에 맞추거나, 덜어낸 내용을 폼에 되돌려 짝을 맞춘다.**

**주석은 트리거와 함께 고쳤다.** concurrency 주석이 "PR 이 열린 브랜치에 푸시할 때 겹치는 것을
정리한다" 라고 적혀 있었는데, 트리거를 되돌린 뒤로 그 겹침은 일어나지 않는다. 남은 역할
(같은 PR 브랜치에 연속 푸시할 때 앞 실행을 접는 것)로 고치고, `on:` 위에는 왜 브랜치 푸시를
받지 않는지를 적었다. **트리거를 바꾸면 그 이유를 적은 주석도 같이 움직인다.**

**PR 을 열기 전까지 브랜치는 CI 를 거치지 않는다.** 되돌리기의 대가다. 커밋 전에 로컬에서
`npm run verify` 를 돌리는 것이 1차 방어선이고, CI 는 PR 에서 처음 확인한다.

**`workflow_dispatch` 를 뺐다.** 이미 뜬 run 의 재실행은 Actions 화면에서 되지만, **임의의 브랜치에서
검증을 새로 띄우는 길은 없다.** 필요하면 PR 을 열거나 트리거를 다시 추가한다.
