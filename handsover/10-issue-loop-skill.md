## 1. 출발점 — 문서는 있는데 실행이 없었다

`09` 까지 아홉 세션이 세운 것은 **규칙**이다. 무엇이 게이트이고(`02 §3`), 몇 번까지
반복하며(`03 §3`), 어떤 코멘트를 남기고(`03 §5`), 언제 PR 로 넘어가는지(`03 §6.1`)가 전부
원본에 있었다.

없던 것은 그것을 **순서대로 실행하는 절차**였다. 매 세션 사람이 "이제 verify 돌려" · "이슈에
코멘트 남겨" · "PR 올려" 를 짚어 줘야 했다.

그래서 이번 요청은 규칙을 늘리는 일이 아니라 **있는 규칙을 실행으로 묶는 일**이었다. 이 구분이
이 세션 내내 판단 기준이 됐다 — 스킬에 규칙을 적고 싶어질 때마다 "이건 원본에 이미 있나"를
먼저 봤다.

## 2. 완료한 것

### `.claude/skills/issue-loop/SKILL.md` — 8단계 실행 절차

```
0. 이슈 번호 확정          ← 요청에 없으면 묻는다. 추측해서 고르지 않는다
1. 이슈·원본 읽기
2. 브랜치 생성
3. 구현 → npm run verify   ← FAIL 이면 최대 횟수까지 반복 (03 §2·§3)
4. 이슈에 완료 코멘트       (03 §5 · 03 §6.1-3)
5. 커밋 → 푸시 → PR 생성
6. CI 대기                 (03 §6.2)
7. LLM 검토               ← 구현 컨텍스트 없는 별도 검토자가 PR 에 코멘트 (02 §5)
8. 사람 검증 요청하고 멈춘다 ← 지적을 고치지 않는다. 판단은 사람 몫 (02 §6)
```

**규칙을 복사하지 않았다.** 코멘트 양식조차 스킬에 옮겨 적지 않고, 쓰기 직전에
`sed -n '/^### 완료 코멘트/,/^### 시도 횟수 초기화/p' docs/harness/03-loop.md` 로 원본을 열어
읽게 했다. 저장소가 반복해 못박은 "두 벌이 되는 순간 어느 쪽이 맞는지 알 수 없어진다"를
스킬에도 적용한 것이다.

스킬이 **더하는** 것은 넷뿐이다.

1. 실행 순서와 정확한 `git`·`gh` 명령
2. `git fetch origin main` 을 브랜치 생성 전에 — Protect 가 merge-base 기준이라 빼먹으면
   엉뚱한 파일이 변경으로 잡힌다 (`scripts/verify/check-protected.ts`)
3. `gh pr checks --watch` 로 CI PASS 를 기다린 뒤 LLM 검토 (`02 §5` 의 시점 규칙)
4. 코멘트를 쓸 때 부실해지기 쉬운 칸을 짚는 것 — 종료 조건의 "확인 결과" · `판단 필요` ·
   `판정이 비는 자리`

### `03 §3`·`§7` — 미정 1번 폐기

```diff
-- 폼을 거치지 않은 Issue는 최대 횟수가 적혀 있지 않다 (§7 미정 1번).
+- 폼을 거치지 않아 6번 칸이 없는 Issue는 폼 기본값인 3회로 본다.
```

`09 §5` 4번이 "세 세션 연속 이월"로 적어 둔 항목이다. 폼 드롭다운이 이미 3회를 기본으로
고르고 있으므로 같은 값을 폼 밖에 적용했다. **`§7` 미정 목록이 비었다** — 이 저장소에 미정
항목이 하나도 없는 것은 처음이다.

계기는 사람의 지적이었다: *"스킬이 원본보다 더 엄격한 규칙을 새로 만들지 않게 해줘."*
스킬 초안은 폼 없는 Issue 를 만나면 "사람에게 몇 회로 할지 묻는다"였는데, 그건 `AGENTS.md §0-4`
를 따른 것이라 발명은 아니었다. 다만 **규칙이 스킬에 살면 안 된다**는 지적은 맞았다. 그래서
스킬을 고치는 대신 원본을 고치고 스킬이 그것을 참조하게 했다 (`00-ssot.md §0-3` 의 순서).

### `02 §5` LLM 검토 — 분리된 검토자로

`02 §5` 는 이 층의 한계를 스스로 적어 뒀다 — *"자기 변경을 자기가 훑은 것이므로 통과 판정으로
읽지 않는다."* 구현한 컨텍스트에는 "왜 이렇게 했는지"가 이미 들어 있어서, 밖에서 보면 이상한
선택이 안에서는 자연스러워 보인다.

그래서 검토를 **구현 컨텍스트가 없는 별도 에이전트**에게 맡기고, 그 검토자가 PR 에 **직접**
코멘트하게 했다. 구현한 쪽이 받아서 옮겨 적으면 그 사이에 표현이 부드러워지는 것을 막을 방법이
없다.

검토자에게 주지 않는 것을 스킬에 표로 명시했다 — 구현 과정의 판단 · 완료 코멘트의 작업 내용 ·
"여기는 이미 봤다"·"이건 의도한 것이다" 같은 안내. 마지막이 특히 중요하다. 그 한마디가 곧
검토자가 볼 자리를 좁히는 일이다.

**원본은 고치지 않았다.** `02 §5` 의 실행자는 "AI. 로컬에서 검토하고 결과를 그 PR 에 코멘트로
남긴다" 이고 *어느* AI 인지는 열려 있다. 서브에이전트도 AI 이고 로컬이고 PR 에 남긴다 —
규칙 변경이 아니라 실행 방법이다.

### `AGENTS.md §1` — 진입 게이트

`이슈 처리해줘` 를 받으면 구현에 들어가기 전에 **스킬을 쓸지 먼저 묻는다.**

| 답 | 진행 |
|---|---|
| 쓴다 | 스킬로 끝까지 — 브랜치 · 구현 · 검증 · Issue 코멘트 · 커밋 · 푸시 · PR · CI · LLM 검토 |
| 쓰지 않는다 | 수동. 커밋 · 푸시 · PR 은 `§3` 대로 따로 요청받아서 |

묻는 이유는 **두 경로의 권한이 다르기** 때문이다. 스킬 경로는 그 호출을 커밋·푸시·PR 생성의
요청으로 본다 — `03 §6.1` 이 사람의 요청을 요구하는 자리를 맨 앞에서 한 번에 당겨 받는
구조다. 잘못 고르면 되돌리기 어려운 쪽도 그쪽이다.

**절 번호를 밀지 않으려고 `§1` 의 하위 절로 넣었다.** `AGENTS.md §0` 과 `§3` 을
`02-verification.md §4` 와 `03-loop.md §6.1` 이 참조한다. 새 절을 `§2` 로 만들었으면 두 문서가
깨졌다.

## 3. 어떻게 좁혀갔나 — 판단이 갈렸던 다섯 곳

1. **스킬에 규칙을 적지 않았다.** 코멘트 양식을 스킬에 넣으면 읽기는 편하다. 그러나 `03 §5` 가
   바뀌면 스킬이 조용히 낡는다. `sed` 로 원본을 여는 쪽이 한 번 더 손이 가지만, 낡지 않는다.
   `AGENTS.md §0-2`("절 단위로 읽는다")가 이미 같은 방식을 쓰고 있어 낯설지도 않다.
2. **"커밋·푸시는 요청받았을 때만"(`03 §6.1`)과 정면으로 부딪히는 자리를 명시했다.** 한마디로
   끝까지 가려면 이 제한을 넘어야 한다. 숨기지 않고 스킬 「권한」 절에 *"이 스킬의 호출이 그
   요청이다"* 로 적었다. 규칙을 무시한 게 아니라 요청 시점을 앞으로 당긴 것이라는 해석을
   문서에 남겨야, 다음 사람이 읽고 판단할 수 있다.
3. **베이스라인 대조 실행을 생략했다.** 스킬 없는 에이전트로 같은 이슈를 돌리면 경쟁하는
   브랜치와 PR 이 하나 더 생긴다. 게다가 스킬 없는 쪽은 `§6.1` 대로 푸시 직전에 멈추는 것이
   정답이라 대조 가치가 낮다. 실행 전에 사람에게 이유를 대고 건너뛰었다.
4. **테스트 이슈를 실제 결함으로 만들었다.** PR #14 의 LLM 검토 지적 1번(`getAdjustSheet` 가
   `quantity > 0` 로트만 나열해 "장부 0 · 실물 있음"을 입력할 자리가 없다)을 Issue #15 로
   올렸다. 가짜 이슈로 돌리면 스킬은 검증되지만 저장소에는 쓰레기가 남는다. 실제 결함이면
   테스트가 곧 작업이 된다 — 그리고 `08 §5` 가 남긴 "LLM 검토 3건 미처리" 중 하나가 줄었다.
5. **하네스 정책 판단은 손대지 않고 보고했다.** 검증 에이전트가 짚은 "낱개 단계를 계속 돌려
   다 통과시킨 뒤 `verify` 를 1회만 돌리면 언제나 1차 시도로 끝난다"는 실질적으로 최대 횟수
   우회 구멍이다. 고치려면 `02 §2` 나 `03 §1` 을 건드려야 하는데 원본에 근거가 없다.
   `AGENTS.md §0-4` 대로 없다고 보고만 했다.
