## 1. 완료한 것

### 02 / 03 책임 경계 재정의

`02`와 `03`을 가르는 기준을 한 문장으로 잡았다.

> **"한 번의 `npm run verify` 실행 안의 일"이면 02, "그 실행을 몇 번 다시 돌릴지의 일"이면 03.**

이 기준으로 `02-verification.md §0` 표를 손봤다. 기존에 "반복 구현 절차 (`03-loop.md`, 미작성)"
한 줄로 뭉뚱그려 있던 것과, 짝이 비어 있던 "Issue 단위 검증의 형식과 대응 규칙" ·
"실패했을 때 멈추는 지점" 두 행을 03과 안 겹치게 재정리했다.

| 정한다 (02) | 정하지 않는다 → 03 |
|---|---|
| 게이트와 경고의 구분, 검사 불능의 처리 | 최대 반복 횟수와 그 출처 |
| Issue 단위 검증의 형식과 대응 규칙 | 반복을 멈추고 사람에게 넘기는 시점과 형식 |
| 한 번의 실행 안에서 어느 단계가 멈추면 뒤 단계를 건너뛰는가 | 재시도 자체를 멈추는 기준 |

세 번째 행이 핵심이었다. 기존 "실패했을 때 멈추는 지점"은 **단일 실행 내 조기 종료**(`&&`로
연결된 단계가 첫 실패에서 멈추는 것)와 **반복을 멈추는 기준**(몇 번째 시도에서 포기하는가)을
구분 없이 가리키고 있어서, 그대로 두면 02와 03이 같은 말을 두 번 정하게 됐다.

### `00-ssot.md` — `NEEDS_HUMAN`을 공통 신호로 확장

`03-loop.md §4`에서 반복을 멈추는 네 사유(보호 경로·충돌·범위 초과·횟수 소진)를 전부
`NEEDS_HUMAN`으로 처리하기로 하면서, 정의 원본인 `00-ssot.md §4`가 좁았다는 게 드러났다.
기존 정의는 "충돌이 확인되면"으로 시작해 **충돌 전용**이었다.

사람에게 두 가지 방향을 물었다.

1. `00-ssot §4`도 함께 넓힌다 (트리거·형식은 상황마다 다른 원본이 정하는 공통 신호로 재정의)
2. `00-ssot`은 충돌 전용으로 두고 03이 다른 이름을 쓴다

**1번으로 확정.** 기존 4항목 형식(충돌한 두 지점 등)은 그대로 두고, 그 위에 "이 신호는
충돌 말고 다른 이유로도 쓰인다"는 트리거 표 한 단을 얹었다.

```
### `NEEDS_HUMAN` 선언

`NEEDS_HUMAN`은 자동화된 판단이나 반복을 멈추고 사람에게 넘길 때 선언하는 공통 신호다.
무엇이 이 신호를 트리거하는지, 어떤 형식으로 보고하는지는 상황마다 다른 원본이 정한다.

| 트리거 | 정의 위치 |
|---|---|
| 원본 간 충돌 (Issue ↔ SSOT · SSOT ↔ SSOT) | 본 절 (§4) — 아래 4항목 형식 |
| 반복 구현 중 정지 사유 | docs/harness/03-loop.md |
```

함께 갱신한 것:

- §1 상태: 구현·검증 루프 `추후 생성` → `확정`
- §2: `### 구현·검증 루프` 경계 절 신설. "검증 항목의 내용이나 게이트·경고의 구분은 다루지
  않는다. 그것은 `02`의 몫이다" 로 역방향 경계도 명시
- §2 검증 규칙 절의 "멈추는 지점을 정한다"도 "한 번의 실행 안에서 어느 단계가 멈추면 뒤
  단계를 건너뛰는지"로 좁혀서 위 세 번째 행과 표현을 맞춤
- §3 "현재 없는 책임 영역": 마지막 남은 행(구현·검증 루프)이 없어져 "현재 모든 책임 영역에
  원본이 있다"로 정리

## 2. 어떻게 좁혀갔나

| 회차 | 무엇이 문제였나 | 어떻게 바꿨나 |
|---|---|---|
| 1 | "03-loop 계획을 세워달라"는 요청에 초안 파일을 바로 만듦 | **삭제하고 계획(표·목록)만 텍스트로 다시 제시** — 승인 전에는 파일을 쓰지 않는다 |
| 2 | 02 §0 표에 03과 겹치는 "멈추는 지점" 행이 그대로 남아 있었음 | "한 번의 실행 안" vs "재시도 자체"로 표현을 갈라 02·03 양쪽에 반영 |
| 3 | §3 최대 횟수를 `npm run verify` 실행 횟수로 셀 뻔함 | "구현 + 검증"을 1회로 묶고, 기본값 3회로 1~3차 예시를 붦 |
| 4 | 시도 횟수 카운트 시점이 "재구현 시작 후"였음 | "검증이 끝나는 시점"으로, 이어서 "PASS든 FAIL이든 무관"으로 일반화 |
| 5 | 네 개 정지 사유의 처리가 제각각(승인 대기·범위 요청·판단 요청 등)이었음 | 전부 `NEEDS_HUMAN`으로 통일 — 대신 `00-ssot §4`의 정의 자체를 넓혀야 앞뒤가 맞음을 확인하고 승인받음 |
| 6 | `NEEDS_HUMAN`이 구현 도중(검증 전)에도 걸릴 수 있는데 흐름도가 검증 이후만 다뤘음 | "구현 중 §4 즉시 사유 발생?" 분기를 흐름도 앞단에 추가, 이 경우도 시도 1회로 셈 |
| 7 | 보고 위치가 미정 목록에 있었음 | "해당 Issue의 코멘트"로 확정, 미정 목록에서 제거 후 재번호 |

1번이 이번 세션에서 제일 중요한 교정이다. **계획을 요청받았을 때는 파일을 쓰지 않는다.**
반복(iteration)을 다루는 문서를 쓰면서 정작 세션 자신의 반복 절차에서 "요청 범위를 벗어난
산출물"을 냈다는 게 아이러니였다.
