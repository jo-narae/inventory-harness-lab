## 1. 완료한 것

### CI 를 모든 브랜치로

`.github/workflows/verify.yml` 의 트리거를 넓혔다.

```yaml
on:
  push:
    branches: ['**']   # 이전: [main]
  pull_request:
  workflow_dispatch:

concurrency:
  group: verify-${{ github.head_ref || github.ref_name }}   # 이전: verify-${{ github.ref }}
  cancel-in-progress: true
```

푸시 트리거가 `main` 하나뿐이라, 작업 브랜치는 PR을 열기 전까지 검증을 거치지 않았다.
태그는 제외한다 — 검증 대상은 브랜치의 코드다.

concurrency 그룹을 브랜치 이름으로 바꾼 이유는 중복이다. `push` 와 `pull_request` 는 `github.ref` 가
서로 다르므로(`refs/heads/x` vs `refs/pull/N/merge`), PR이 열린 브랜치에서는 같은 커밋이 두 번 검증됐다.
`head_ref || ref_name` 은 두 이벤트 모두 브랜치 이름으로 떨어져 한 그룹에 묶인다.

### 보호 경로 승인 — 커밋 트레일러

`ALLOW_PROTECTED` 환경변수는 로컬에만 있고 이력에 남지 않아 CI가 볼 수 없었다.
그래서 보호 파일을 건드린 브랜치는 병합 전까지 CI가 계속 빨간불이었다.

`base..HEAD` 커밋 메시지의 트레일러를 승인으로 읽게 했다.

```
Approved-Protected: docs/harness/00-ssot.md scripts/verify/check-protected.ts
```

| 방법 | 유효 범위 |
|---|---|
| 커밋 트레일러 `Approved-Protected:` | merge-base..HEAD. 로컬과 CI 양쪽 |
| 환경변수 `ALLOW_PROTECTED` | 그 실행 한 번. 로컬만 |

승인된 항목은 출처를 함께 출력한다. 조용히 통과하지 않는다.

```text
⚠️  승인됨  docs/harness/00-ssot.md   하네스 핵심 규칙 (docs/harness/)   ← 커밋 b07d1c7
      사람이 명시적으로 승인한 변경으로 본다 (§5)
```

### 승인 규약을 SSOT 에 정의

`docs/harness/00-ssot.md §5` 끝에 `### 승인 기록` 절을 추가했다. 방법·형식·유효 범위,
CI에 환경변수를 두지 않는 이유, 그리고 한계를 적었다.

스크립트 주석에서는 방법과 형식을 걷어내고 SSOT를 가리키게 했다. 경로 목록을 옮겨 적지 않는 것과
같은 이유다 — 두 벌이 되면 어느 쪽이 맞는지 알 수 없어진다.

## 2. 왜 헤맸나 — 순서가 뒤집혔다

이번 세션의 실질적 교훈은 기능이 아니라 **도입 순서**다.

보호 경로 검사(Protect)를 CI보다 먼저, 그리고 **사람 승인 파트 없이** 도입한 상태였다.
그 결과 CI를 모든 브랜치로 넓히는 순간, 검사가 자기 자신을 만드는 브랜치를 막았다.
`docs/harness/00-ssot.md` 와 `scripts/verify/check-protected.ts` 가 둘 다 보호 경로이기 때문이다.

| 순서 | 한 일 | CI | run |
|---|---|---|---|
| 1 | push 트리거를 모든 브랜치로 | — | — |
| 2 | 막힘 발견 → 브랜치 이름을 워크플로에 박아 임시 승인 | ✅ | 32676656890 |
| 3 | 임시 승인 revert | ❌ | 32676979385 |
| 4 | 트레일러 승인으로 재설계 | ✅ | 32678000801 |
| 5 | 승인 규약을 SSOT 에 정의 | ✅ | 32678844118 |
| 6 | PR #3 → `main` 병합 | ✅ | 32679109743 |

2~3번이 통째로 낭비였다. 워크플로에 브랜치 이름을 하드코딩한 커밋(`e9df362`)과 그 revert(`dd44ae1`)가
이력에 남아 있다. 되돌렸으니 동작에는 영향이 없지만, 읽는 사람에게는 설명이 필요한 흔적이다.

원인은 하나다. **승인 경로 없이 차단 장치만 먼저 세웠다.** 차단만 있고 통과 수단이 없으면,
그 장치를 손보는 작업 자체가 불가능해진다.

## 3. 다음에 같은 것을 만든다면

한 번에 요청한다. 다음 발화문이면 위 2~3번을 건너뛴다.

> SSOT를 기준으로 보호 경로 변경을 검사하는 Protected를 만들어줘.
> 승인되지 않은 보호 경로 변경은 실패하고, 사람이 승인한 변경은 로컬과 CI에서 통과할 수 있게 해줘.
> 승인 방법도 SSOT에 함께 정의해줘. Protected는 `npm run verify` 의 첫 단계에서 실행되게 해줘.

이 한 문장에 필요한 것이 다 들어 있다.

| 조각 | 무엇을 정하나 |
|---|---|
| SSOT를 기준으로 | 경로 목록을 코드에 적지 않는다 |
| 승인되지 않은 변경은 실패 | 차단 조건 |
| **로컬과 CI에서 통과** | 승인 경로가 두 곳 모두 필요하다는 것 — 이번에 빠졌던 조각 |
| 승인 방법도 SSOT에 | 규약의 원본 위치. 코드 주석이 원본 노릇 하는 것을 막는다 |
| verify 첫 단계 | 파이프라인 위치 |

만드는 순서도 뒤집지 않는다.

```text
원본(SSOT §5 + 승인 기록) → 스크립트 → CI 트리거
```

승인 규약이 원본에 먼저 있으면, 스크립트는 그것을 읽기만 하면 되고 CI는 아무 설정도 필요 없다.
실제로 최종 상태의 `verify.yml` 에는 승인 관련 설정이 한 줄도 없다.

## 5. 주의사항

**승인은 기록이지 잠금장치가 아니다.** 커밋 메시지는 누구나 적을 수 있고, AI도 적을 수 있다.
이 장치가 막는 것은 승인 없는 변경 자체가 아니라, 승인 없이 **조용히** 지나가는 일이다.
더 강한 강제가 필요하면 서명 커밋 검증이나 저장소 설정의 필수 리뷰어로 따로 세운다. SSOT에도 그렇게 적었다.

**트레일러는 `merge-base..HEAD` 범위에서만 유효하다.** 병합되어 merge-base가 옮겨가면 범위 밖으로
빠지지만, 그때는 변경도 함께 base에 들어가므로 검사 대상이 아니다. squash 병합이면 트레일러가
병합 커밋 메시지로 합쳐진다 — 승인 이력을 남기려면 병합 방식에 유의한다.

**검사는 스스로를 잡는다.** `scripts/verify/` 가 보호 경로라, 이 스크립트를 고칠 때마다 승인이 필요하다.
의도한 동작이다.

**CI 경고 1건 미해결.** `actions/checkout@v4` · `actions/setup-node@v4` 가 Node 20 타깃이라
러너가 24로 강제 실행 중이라는 GitHub 공지가 매 run 마다 붙는다. 실패는 아니다. `@v5` 로 올리는 작업은
이번 범위 밖이라 손대지 않았다.
